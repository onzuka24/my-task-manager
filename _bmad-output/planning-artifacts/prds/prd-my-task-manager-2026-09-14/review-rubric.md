# PRD Quality Review — my-task-manager

## Overall verdict

ビジョン (§1)、非目標 (§5)、MVP の切り方 (§6.1) は、solo/hobby の PRD としては例外的に強い。仮説が一つに絞られ、addendum が採否の理由を残しており、「何を作らないか」が実際に下流を縛る形で書かれている。危ういのは **done-ness** と **v1 内部の整合性**である。MVP に入っている唯一の**介入** (FR-15) は、提示形式・選択肢・終端条件のいずれも定義されておらず、しかも §3 用語集・FR-6・FR-15 の三箇所が**休息**中の**現在地**について互いに矛盾している。加えて §4.5 と §5/FR-2 の水準で「FR が存在しない約束」が二つある (固着の検出、全体像の開示面)。アーキテクチャと UX に渡す前に、v1 に属する矛盾 (下記 critical / high) だけは解消すべきである。

## Decision-readiness — adequate

判断材料としてはよく機能している。§6.2 の `[NOTE FOR PM] **交差**はユーザーが最も強く訴えた痛みであり、v1 に含まれないことは意図的な先送りである` は、まさに読者が反論したくなる一点に置かれており、安全な場所への飾りではない。§6.3 の `v1 ではこの誤りを許容する` も、代償を名指しして受け入れる形になっている。addendum §2.1/§2.2/§2.3 は「捨てた選択肢とその理由」を表にしており、トレードオフが中立に均されていない。

弱いのは §10 の構成である。5 つの問いはいずれも本物の未決事項だが、**すべてが v2 以降に割り当てられており、v1 を実際に止めうる未決事項が一つも載っていない**。v1 に入る FR-15 の「強い提示形式」と「閾値の初期値」は未定のまま §10 に現れず、問い 2 はむしろ `v2 の課題` と明記されている。結果として §10 は「v1 は着手可能」という誤った安心を与える。

### Findings

- **high** v1 を止める未解決の問いが §10 に一つも無い (§10 問い2、FR-15) — 問い2は「選択するまで消えない」と「入力先を奪わない」の両立を `v2 の課題` としているが、この制約は §7.2 で `**介入** (FR-14、FR-15)` の双方に掛かっており、FR-15 は v1 スコープ (§6.1) である。FR-15 の閾値初期値も §10 に無い (FR-17 の判定期間初期値は問い3として載っているのに対し非対称)。*Fix:* 問い2を「v1 の課題 (FR-15)」と「v2 の課題 (FR-14)」に分割し、「連続作業時間の閾値初期値」を新たな問いとして追加する。
- **medium** FR-16 を先送りする理由が FR-16 に当てはまらない (§6.2) — `**FR-14 交差介入 / FR-16 決定の記録** — v2。**本日計画**と**現在地**の双方を必要とするため v1 では成立しない` とあるが、FR-16 は `**介入**に対してユーザーが行った選択は記録される` であり、**休息**の**介入** (FR-15、v1) にも掛かる。本日計画を必要としない。先送り自体は妥当でも、理由が偽であるため下流が「v1 の休息介入の選択は記録不要」を導けない。*Fix:* FR-16 の先送り理由を「v1 では記録の活用先が無い (§10 問い5) ため」に差し替えるか、FR-15 の応答のみ v1 で記録する縮退を §6.3 に足す。

## Substance over theater — strong

ペルソナを置かず JTBD のみにした判断 (§2 `合意形成のためのペルソナ定義は行わず`) は solo として正しく、ペルソナ劇場が無い。§1 のビジョンは他の PRD に差し替え不能である — `切り替えるべき場面で固着して惰性のまま時間を溶かし`、`二つのタスクに同時に家賃を払っている` は、この作者のこの失敗からしか出てこない。設計上の三つの賭けは addendum §4 で出自 (放棄されたプレーンテキスト TODO リスト、本人の発話) に紐付けられており、一般論の設計原則の転記ではない。§8 の NFR も `システムは高速でなければならない` 型の空文ではなく数値を持つ。

### Findings

- **low** §8 の数値の由来が無く、`[ASSUMPTION]` も付いていない (§8) — `CPU 1% 未満・メモリ 100MB 未満`、`300ms 以内` は作者が確認した値ではなく推論であろうが、§11 前提一覧には現れない。§8 自身が `当該上限は v1 の技術選定に対する制約として働く` と書いており、誤っていれば技術選定をやり直す種類の数値である。*Fix:* 三つの数値に `[ASSUMPTION]` を付し §11 に集約する (特にメモリ 100MB は選定を左右する)。

## Strategic coherence — adequate

テーゼは明確で、MVP の切り方はそこから演繹されている。§6.1 の `v1 が検証する仮説は一つである — 中断地点を記録し再開時に全体の中の位置を返すことで、前のタスクを実際に頭から手放せるようになるか` は、4.1/4.2/4.3 の採用と 4.4/4.5/4.6/4.7 の先送りを過不足なく説明する。「楽なものから作る」ではなく「仮説を最も安く検証できる構成」になっている。逆指標を置いていることも、この製品の性格 (可視化=罪悪感) と噛み合っている。

破れ目は一箇所、**FR-15 だけがこの論理の外にある**。FR-15 は §6.1 の仮説に寄与せず (§9 のどの SM も FR-15 を検証対象に挙げていない)、代わりに §6.3 の縮退により `**切り替え**を宣言せずに離席した場合、作業継続中とみなされ**介入**が誤発火する` を v1 に持ち込む。誤発火する強い割り込みは、SM-1 (継続利用 = 放棄されないこと) を最も直接に脅かす事象であり、しかも SM-1 は v1 の最初の成功条件とされている。

§9 の検証主張も緩い。SM-1 は `FR-1、FR-2 を検証する` と書くが、1 か月の継続利用は製品全体の生存であって、300ms やオーバーレイの最小表示を切り分けて検証しない。

### Findings

- **high** FR-15 が v1 の仮説に属さないまま MVP に入っている (§6.1、§6.3、§9) — §6.1 は検証仮説を一つに絞ったうえで `最も安価にこの一点を検証できる構成を v1 とする` と宣言しているが、FR-15 はその一点に寄与せず、§6.3 が認める誤発火リスクを SM-1 に対して持ち込む。含めるなら理由を本文に書くべきで、書けないなら v2 が正しい。*Fix:* §6.1 に FR-15 を入れる理由 (身体的 JTBD は仮説検証と独立に緊急、等) を一文で明示するか、FR-15 を v2 に送り §6.3 を削除する。
- **medium** SM-1 の検証対象の主張が過大で、測定手段が無い (§9 SM-1) — `導入から 1 か月後も日常的に使用している` は FR-1/FR-2 を分離検証しない。また「日常的に使用している」を判定する記録が製品側にもプロセス側にも規定されていない (§5 が禁じるのは表示であって記録ではないので、内部記録は非目標と衝突しない)。*Fix:* SM-1 の検証対象を「製品全体」とし直し、判定方法 (例: 1 か月後に週あたり起動日数を目視で確認) を一文添える。
- **medium** 中核仮説 SM-2 に基準点も逆指標も無い (§9) — SM-2 は `前の**タスク**が頭に残り続ける状態が減ったと自覚できる` という事前/事後比較を要求するが、導入前の状態を記録する指示がどこにも無い。v1 の存在理由である指標が、v1 開始後には原理的に測れなくなる。さらに逆指標 SM-C1/SM-C2 はいずれも `SM-1 を相殺する` とされ、最も自己申告バイアスを受けやすい SM-2 を相殺するものが無い。*Fix:* 「導入前に現状の自覚を 2〜3 行で書き留める」を SM-2 の前提として明記し、SM-2 用の逆指標 (例: 中断メモの記入率が下がっていないか) を一つ置く。

## Done-ness clarity — thin

FR-1、FR-4、FR-6 前半、FR-7、FR-8、FR-17 は良い。`300ms 以内`、`Esc キー単独で閉じられる`、`**ステップ**を持たない**タスク**は作成できない (最低 1 個)`、`省略しても**切り替え**は完了する` は、いずれもそのままテストになる。

しかし MVP に入る範囲で、実装者が手を止める箇所が複数ある。最も重いのは**休息**中の**現在地**の扱いで、§3・FR-6・FR-15 が三者三様である。次に、v1 唯一の**介入**である FR-15 が、何をどう提示し何をもって終わるのかを一切規定していない — §4.6 の説明は `**介入**は意図的に強い提示形式を取る` と述べ、FR-14 は選択肢二つと消えない条件を持つが、FR-15 は持たない。また FR-5 は `追加または分割できる` と宣言しながら、結果条件は追加 (連番再計算) しか押さえていない。

FR-2 と FR-13 の結果箇条には、要件文の言い換えに留まるものが混じる。FR-13 の `**交差**の検出には**本日計画**と**現在地**の双方が必要であり、いずれかを欠く場合は検出されない` は §3 の**交差**の定義から自動的に従う命題であって、新しい検証条件を足していない。

### Findings

- **critical** 休息中に**現在地**が在るのか無いのかが三箇所で矛盾する (§3、FR-6、FR-15) — §3 は `**休息 (Rest)** — 作業から離れている状態。**現在地**を保持したまま遷移する`、FR-6 の結果は `**現在地**が存在しない状態 (未着手・**休息**中) を表現できる`、FR-15 の結果は `**休息**に入った時点の**現在地**は保持され、復帰時に FR-8 と同じ形式で提示される`。FR-6 と FR-15 は同じ v1 スコープにあり、データモデル (現在地を null にするのか、保持したまま状態フラグを持つのか) が正反対に読める。*Fix:* §3 と FR-15 の「保持」に統一し、FR-6 の結果から `**休息**中` を削除して `未着手` のみとする (あるいは「保持された現在地」と「アクティブな現在地」を別概念として §3 に足す)。
- **high** v1 唯一の**介入** (FR-15) に提示形式・選択肢・終端条件が無い (FR-15、§4.6、§7.2) — FR-14 には `選択肢のいずれかが選ばれるまで**介入**は消えない` があるが、FR-15 の結果三つは現在地保持・閾値変更・本日計画非依存のみで、ユーザーが何を選ぶのか、無視できるのか、スヌーズがあるのか、**休息**の終了をどう検出するのかが一切無い。§7.2 の入力奪取禁止だけが掛かる。v1 で実装する唯一の割り込みが、この PRD で最も未定義な FR になっている。*Fix:* FR-15 に選択肢 (例: 「休息に入る」「n 分後に再提示」) と終端条件、および**休息**からの復帰トリガを結果条件として追加する。
- **high** FR-5 の「分割」に検証可能な結果が無い (FR-5) — 結果は `**ステップ**の追加により後続の**ステップ**の連番が再計算されても、**現在地**は同一の作業単位を指し続ける` の一つのみ。分割時に**現在地**が前半・後半どちらを指すのか、当該**ステップ**に付いた**中断メモ** (§3 で `ステップに対して 0..1`) がどちらへ移るのかが未定義である。FR-5・FR-7・FR-8 はすべて v1 であり、この三者の交点は再開体験そのものに直結する。*Fix:* 分割時の**現在地**と**中断メモ**の帰属を結果条件として明記する。
- **medium** FR-13 の「移行を要求している」の算定方法が未定義 (FR-13、FR-9) — FR-9 が**本日計画**に与えるのは `想定時間` であって絶対時刻ではない。したがって「次のタスクへ移るべき時刻」は開始時刻からの累積で導く必要があるが、その規則も、遅延が累積したときの扱いも書かれていない。FR-13/FR-14 の発火条件が計算不能である。*Fix:* FR-9 の結果に「**本日計画**は開始時刻を持ち、各**タスク**の移行期待時刻は想定時間の累積で定まる」を足す。
- **medium** FR-14 の「猶予」が未定義 (FR-14) — `「完了させてから移行する」が選ばれた場合、猶予の終了時に再度**介入**が発せられる` の猶予は、長さも決定主体 (固定値/ユーザー設定/ステップの残り想定時間) も規定されておらず、§3 にも無い新語である。このままではテストが書けない。*Fix:* 猶予の既定値と変更可否を結果条件に足すか、§10 の未解決の問いに繰り上げる。
- **medium** FR-12 が算出する**ずれ**を消費する FR が存在しない (FR-12) — 結果は `**ずれ**は当日中に算出され、翌日以降の振り返りを待たない` のみで、算出された**ずれ**がユーザーに提示される経路が無い。§4.6 の**介入**は**交差**と**休息**の二契機に限定され、**ずれ**は契機に入っていない。JTBD `一日の計画から逸脱したことに、その日のうちに気づきたい` は「算出」ではなく「気づく」を求めており、現状の FR 群では満たされない。*Fix:* FR-12 に提示経路 (オーバーレイ上の表示か、**ずれ**が閾値を超えたときの扱いか) を結果条件として足す。
- **medium** **中断メモ** 0..1 の上書き規則が無い (FR-7、§3) — §3 は**中断メモ**を `ステップに対して 0..1` と定義するため、同じ**ステップ**から二度目の**切り替え**を行うと既存メモの扱い (上書き/追記/前回分の表示) が問題になるが、FR-7 はこれに触れていない。v1 の中核機能でありながらデータモデルが一意に決まらない。*Fix:* 二度目以降の記録時の挙動を FR-7 の結果条件に明記する。
- **medium** 「数秒で完結」がどの FR の結果条件にもなっていない (§4.1、UJ-1) — §4.1 は `呼び出しから記録完了までの操作は数秒で完結しなければならない` と書き、UJ-1 も `止まった地点を数秒で記録して離脱する` と書くが、FR-1 が押さえるのは入力受付開始までの 300ms のみで、FR-7 (中断メモ記録) には時間・操作数の条件が無い。v1 の設計原則が検証不能なまま散文に留まっている。*Fix:* FR-7 に操作数または所要時間の上限 (例: 呼び出しから離脱まで n キーストローク以内) を結果条件として足す。
- **low** 結果条件が要件の言い換えに留まる箇所 (FR-2、FR-13、FR-16) — FR-2 の `初期表示に含まれるタスク情報は**現在地**が指す 1 件のみである` は要件文とほぼ同義 (第三箇条の位置情報の例外規定だけが情報を足している)。FR-13 の第一箇条は §3 の**交差**の定義から自動的に従う。FR-16 の `すべての**介入**は選択で終端する` は FR-14 第二箇条の再掲である。*Fix:* 言い換え箇条は削るか、観測可能な境界条件 (例: FR-2 なら「複数タスクが同時に画面に現れない」) に書き換える。
- **low** FR-3 の耐久境界が PRD 本体に無い (FR-3、§8) — `**常駐プロセス**が異常終了した場合、**現在地**と**中断メモ**は失われない` は、どの時点まで確定しているかを規定しない (入力途中の**中断メモ**は失われてよいのか)。addendum §3.2 に `切り替えの完了時点で確定していること` とあるが、本体の検証条件には反映されていない。*Fix:* 「**切り替え**の完了時点で確定する」を FR-3 の結果条件に引き上げる。

## Scope honesty — adequate

省略は概ね明示されている。§5 非目標は 6 項目すべてに「なぜそうならないか」が付いており、飾りでなく下流を縛る。§6.1/§6.2 は FR-1〜FR-18 を漏れなく v1/v2 に振り分けている (数え上げ済み: 18 個すべてがどちらかに現れる)。§6.3 は縮退を黙って行わず、誤発火という代償を明記している。`[ASSUMPTION]` は 3 件で §11 と往復が成立している。open-items 密度 (未解決 5、ASSUMPTION 3、NOTE FOR PM 2) は hobby/solo の stakes に対して妥当である。

問題は「明示されなかった省略」が二つあることで、いずれも FR の不在という形を取っているため、読者が気づきにくい。

### Findings

- **high** 全体像・一覧を開示する面に対応する FR が無く、§5 と FR-2 が衝突する (FR-2、§5、FR-9、FR-17、FR-18) — FR-2 は `**タスク**の全体像および一覧は、ユーザーの明示的な操作によってのみ開示される` と述べ、開示面の存在を前提にする。FR-9 (その日のタスクを順序付きで選択)、FR-17 (`通常の表示対象から自動的に除外`)、FR-18 (`通常の表示対象へ戻せる`) はいずれもこの面に依存する。しかし §5 は `**一覧性を提供しない。**「今日やること全部」「今週の予定」を一望する画面は設計目標に含まれない` と宣言しており、両者は文字通りには矛盾する。そしてこの面を定義する FR は 4.1〜4.7 のどこにも無い。v1 では FR-2 のみが関係するが、「通常の表示対象」という語は v2 の FR-17/FR-18 の判定基準そのものである。*Fix:* §5 を「常時の一覧表示を持たない (明示操作による開示は FR-2 の範囲で許容する)」に限定し直し、開示面を規定する FR を 4.2 に一つ追加する。
- **high** §4.5 が約束する二つの能力に対応する FR が無い (§4.5、FR-11〜13、addendum §2.1) — §4.5 の説明は `ユーザーが宣言しなかった**切り替え**および固着状態を推定する` と書くが、配下の FR は FR-11 (識別情報の取得と突き合わせ)、FR-12 (**ずれ**)、FR-13 (**交差**) のみで、「宣言されなかった切り替えの推定」も「固着」もどの FR の結果条件にも現れない。addendum §2.1 は、まさにこの二つが検出できることを理由にアクティブウィンドウ観測を採用し `代償として OS 権限・実装量・プラットフォーム依存・プライバシー懸案が最大化する` と認めている。最大コストの技術選定を正当化する能力が、要件として書かれていない。*Fix:* 固着の検出と未宣言の切り替えの推定を FR として起こす (v2)。書けないなら §4.5 の説明と addendum §2.1 の判断根拠を修正する。

## Downstream usability — adequate

§0 が `本文書を入力とする下流のワークフロー (アーキテクチャ設計、UX 設計、エピック/ストーリー分解)` を明示しており chain-top の PRD であるため、この次元は重い。基礎は整っている: FR ID は 1〜18 で連番・重複なし、相互参照 (FR-10 → FR-1/7/8/15、FR-15 → FR-8、§7.1 → FR-11、§8 → FR-1/FR-3、§10 → FR-14/FR-16/FR-17/§7.1/§7.2) はすべて解決する。UJ-1〜3 はいずれも主人公 (Onzuka) が明示され、浮いた UJ が無く、各 UJ が少なくとも一つの FR から参照されている。`[ASSUMPTION]` の往復も成立している。各節は単体で抜き出しても意味が通る。

引っかかるのは、アーキテクチャがそのまま鵜呑みにすると誤る記述が §8/§10 にあること、および用語集の外で用語のように振る舞う語があることである。

### Findings

- **high** プラットフォーム非依存の主張が v1 の FR と矛盾する (§8 可搬性、§10 問い1) — §8 は `**観測** (4.5) を除くすべての機能はプラットフォーム非依存に設計する。**観測**のみが OS 固有実装を必要とする` と書くが、FR-1 (`いかなるアプリケーションが最前面にあっても、単一のグローバルホットキー`)、FR-3 (`ログイン時に自動的に起動`)、FR-15/§7.2 (最前面での強い提示と入力奪取の回避) は、いずれも OS 固有の統合を要する v1 の要件である。この誤りは §10 問い1 の `**観測**は v2 以降であるため v1 の着手は阻害されない` に直結しており、プラットフォーム未確定のまま v1 に着手できるという結論を支えてしまっている。実際には FR-1/FR-3 の時点でプラットフォーム決定が必要である。*Fix:* §8 の可搬性を「ドメインロジックはプラットフォーム非依存、OS 統合点は FR-1・FR-3・FR-11・FR-15 の四つ」と書き直し、§10 問い1 の「v1 の着手は阻害されない」を撤回する。
- **medium** 「観測」が用語集に無いまま用語として太字使用されている (§3、§4.5、§6.2、§7.1、§8、§10、§11) — §3 は `同義語の導入は禁止する` と宣言し、他の全用語は §3 で定義されているが、**観測**は定義されないまま `**観測**により取得した情報は`、`**観測**を無効化した状態で`、`**観測** (4.5) を除く` のように 10 箇所前後で太字の定義語として扱われている。下流が「観測」の外延 (取得対象はアプリ名か、ウィンドウタイトルか、URL か) を §7.1 の保持期限と突き合わせられない。*Fix:* §3 に **観測 (Observation)** を追加し、取得対象の粒度まで定義する。
- **low** 用語集外の未定義語と英語の混在 (§1、§4.5、FR-14、FR-15) — `固着` (§1、§4.5)、`猶予` (FR-14)、`連続作業時間` (FR-15、v2 での定義が無い)、`再入` (FR-2、SM-3、§8) は §3 に無い。また `residue` (§1)、`capture`/`grooming` (§1、§4.7)、addendum の `risk` が未訳のまま混在する。*Fix:* 固着と連続作業時間は §3 に足す (検出対象そのものであるため)。他は日本語に統一する。
- **low** §9 SM-C1 の Markdown が壊れている (§9) — `- **SM-C1: 登録された**タスク**の数。**` は太字の入れ子により、レンダリング時に見出しが崩れる。*Fix:* `- **SM-C1: 登録されたタスクの数。**` とし、内側の強調を外す。

## Shape fit — strong

hobby/solo かつ chain-top という形に正しく合わせてある。ペルソナを置かず JTBD のみとし (§2)、UJ は 3 本の軽量表記に留め (§2.3 `solo 用途のため軽量表記とする`)、SM は定量目標ではなく継続利用と体感に寄せている (§9 `定量的な目標値ではなく継続利用と体感の変化によって評価する`)。単独利用の道具に対して UJ を過剰に積む、あるいはステークホルダー承認・ROI・ロールアウト計画を持ち込むといった over-formalization は無い。一方で、下流が必要とする深度 (用語集、FR の結果条件、非目標、前提一覧、addendum の判断記録) は保たれており、under-formalization にも落ちていない。実現手段を addendum に分離した判断 (§0) も、PRD と技術選定の境界として適切である。所見なし。

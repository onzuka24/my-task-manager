# Addendum — my-task-manager

PRD 本体に含めるべきではないが、下流のワークフロー (アーキテクチャ設計、UX 設計、エピック/ストーリー分解) が必要とする深度の情報を保持する。PRD が「何を」を定義するのに対し、本書は「なぜその選択に至ったか」と「どう実現しうるか」を記録する。本書中の § および FR-n、OQ-n、SM-n は、断りのない限り PRD 本体の節・番号を指す。

## 1. 課題の理論的裏付け

ユーザーが述べた「切り替えた後も前のタスクが頭に残り、新しいタスクに集中できない」という現象は、Sophie Leroy が **attention residue** (注意残余) として報告した概念と一致する (Leroy, S. "Why is it so hard to do my work? The challenge of attention residue when switching between work tasks", *Organizational Behavior and Human Decision Processes*, vol. 109, 2009)。要点は次の二つであり、いずれも本 PRD の設計判断に直接影響している。

- 残余は切り替えの**速さ**では解消しない。前のタスクに対する**クロージャの感覚**が欠けていることが原因である。
- 残余は前のタスクが**未解決のまま**中断されたときに最も強く発生する。

この二点が、FR-7 (中断メモ) と FR-8 (再開時の位置提示) を「速さ」ではなく「完了」に振った根拠である。同時に、これは本製品の中核仮説が既存研究と整合することを意味するが、検証されたことを意味しない — これを検証するのが SM-2 である。

## 2. 検討したが採用しなかった選択肢

以下は PRD の主要な設計判断について、採用しなかった案とその理由を記録する。下流で同じ案が再提案された際の判断材料として用いること。

### 2.1 観測方式

| 選択肢 | 内容 | 判断 |
|---|---|---|
| タイマーのみ | ユーザーの宣言のみを情報源とする | **不採用**。宣言を忘れた時点で確信をもって誤った状態になる。ただし v1 では FR-15 の縮退仕様として事実上これを採用している (§6.3) |
| タイマー + アイドル検出 | キーボード/マウスの無操作を OS から取得 | **不採用**。休息検出は改善するが、**固着** (ブラウザに 40 分いる) は検出できない。ユーザーの痛みの中心が**固着**であるため不足 |
| アクティブウィンドウ観測 | 最前面アプリ/ウィンドウを継続取得 | **採用**。宣言されなかった**切り替え**と**固着**の双方を検出できる唯一の方式。代償として OS 権限・実装量・プラットフォーム依存・プライバシー懸案が最大化する |

この採用根拠を要件として担保するのが FR-20 (**固着**の検出) と FR-21 (未宣言の**切り替え**の推定) である。この二つが v2 で実装されないのであれば、**観測**の採用根拠自体が失われる。その場合はタイマー + アイドル検出への降格を再検討すること。

### 2.2 本日計画の生成方法

| 選択肢 | 内容 | 判断 |
|---|---|---|
| カレンダー連携 | 既存のカレンダー予定から**本日計画**を導出する | **不採用**。二重管理を避けられる利点はあるが、ユーザーの一日がカレンダー上に存在することが前提となり、また外部サービス依存が §7.3 のコスト制約と衝突する |
| 事後記録型 | 計画を立てず、実績から一日の記録を構築する | **不採用**。朝の義務を課さない利点はあるが、**交差**検出には「いつ次へ移るべきか」の事前の期待値が不可欠であり、事後記録では原理的に**交差**を検出できない |
| 朝のリチュアル (**本日計画**の作成) | 毎朝ユーザーが**タスク**を順序付きで並べ、時間配分を与える | **採用**。**交差**検出に必要な事前の期待値を与える唯一の方式。義務化のリスクは FR-10 (未作成時の縮退・非督促) で緩和する |

### 2.3 腐敗の扱い

| 選択肢 | 内容 | 判断 |
|---|---|---|
| 陳腐化マークを付けて表示し続ける | 古い**タスク**に陳腐化の印を付けたうえで一覧に残す | **不採用**。放棄されたプレーンテキスト TODO リストと同じ結果 (罪悪感の山) を、手順を増やしただけで再現することになる |
| 完全に削除する | 期限を過ぎた**タスク**をデータごと消去する | **不採用**。失う不安は新たな摩擦を生み、「消えるくらいなら全部確認しておこう」という grooming の再発を招く |
| 視界から外すがデータは保持 | 表示対象から除外し、データは残す | **採用**。見えないことで罪悪感を断ち、保持することで喪失不安を断つ。両立が可能な唯一の構成 |

## 3. 実現手段に関する下流への申し送り

PRD 本体は能力 (capability) のみを規定し、以下は意図的に記載していない。アーキテクチャ設計の入力として扱うこと。

### 3.1 プラットフォーム依存の境界

OS 固有の実装を要する四つの境界は §8 可搬性に列挙済みである。このうち最も重いのは FR-11 (**観測**) である。

**判断の経緯 — 当初「v1 に FR-11 が含まれないためプラットフォーム決定は v1 の着手を阻害しない」と記載していたが、これは誤りであり撤回する。** FR-1、FR-3、FR-15 はいずれも v1 スコープであり、かつ OS 固有の統合を要する。したがってプラットフォームの決定は v1 の実装着手に先行して必要である (§10 OQ-1)。同じ誤りが再導入されることを防ぐため、撤回の事実をここに残す。
macOS ではアクセシビリティおよび画面収録に相当する権限が、Windows では別系統の API が必要であり、両者に共通の抽象化レイヤは実質的に存在しない。したがって設計上は本機能を差し替え可能な境界として切り出し、未実装・権限未付与のプラットフォームでは無効化した状態で他機能が完全に動作する構成とすること (FR-11 の結果条件に規定済み)。

加えて、v1 の技術選定は二つの制約を同時に満たす必要がある — §8 の待機時メモリ 100MB 未満という上限を守ること、および v2 で FR-11 の**観測**を実装可能であること。この二つは実行基盤の選択肢を強く絞り込むため、v1 着手前に併せて検討すること。

### 3.2 永続化

FR-3 および §8 のデータ堅牢性要件は、**現在地**と**中断メモ**がプロセスの異常終了をまたいで残ることを求める。これは書き込みのタイミング (**切り替え**の完了時点で確定していること) に対する制約であり、記憶方式の選択そのものには制約を置いていない。§7.1 および §7.3 により、端末内保持かつサーバ構成要素なしという条件のみが確定している。

### 3.3 強い提示形式

FR-15 および FR-14 の「選択肢のいずれかが選ばれるまで**介入**は消えない」と §7.2 の「入力先を奪ってはならない」は緊張関係にある。両立の手段は未決定であり、§10 OQ-2 として PRD 本体に記載した。FR-15 が v1 スコープであるため、これは **v1 の UX 設計における課題**である。

## 4. 設計原則の由来

本 PRD の「設計上の三つの賭け」(§1) は、いずれもユーザー自身の失敗経験から導かれており、一般論としての設計原則ではない。下流で原則同士が衝突した際は、以下の出自に立ち返って優先順位を判断すること。

1. **一度に見せるのは「次の一手」だけ。** — 肥大化したプレーンテキスト TODO リストが未来のタスクを大量に可視化し、目の前の一手への集中を奪って放棄に至った経験に由来する。この原則を緩めることは、既知の放棄要因を再導入することを意味する。
2. **タスクは平坦な項目ではなく、順序を持つ工程である。** — 「全体は No.1〜N で、自分は 3 にいる」というユーザー自身の言葉に由来する。再入時に必要な情報は内容ではなく位置である、という主張を含む。
3. **摩擦は capture ではなく grooming にある。** — 書き留めること自体は苦ではないという証言に由来する。したがって入力の高速化に投資しても、この製品の中心的な痛みは解消しない。

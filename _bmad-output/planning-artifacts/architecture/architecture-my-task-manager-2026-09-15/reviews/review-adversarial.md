## クラスタ A — 計時 (AD-8)

AD-8 は「計時はコアが所有する」とだけ述べ、**時計源・刻み・リセット契機・スリープ時の扱いのいずれも規定していない。** FR-15 は v1 唯一の能動機能であり、PRD §6.1 が「利用者の健康を理由とした意図的な例外」として特筆したものである。ここが割れると v1 の目玉が機能しない。

### DP-01 [Critical] 連続作業時間の時計源 — スリープをまたぐか

- **Unit A — `domain/clock.rs` (単調時計の累積器):** コア内に `ContinuousWorkTime { accumulated: Duration, since: Instant }` を持ち、1 秒の tick で `Instant::elapsed()` を足し込む。macOS の `Instant` は `CLOCK_UPTIME_RAW` 相当でスリープ中は進まない。
- **Unit B — `domain/rest.rs` (永続時刻からの差分):** 「一貫性の規約」の「時刻は UTC の ISO 8601 で保持し」「期間は秒の整数」に従い、DB に保存した `last_activated_at`(UTC ISO 8601) と `Utc::now()` の差で連続作業時間を求める。壁時計であるためスリープ中も進む。

**両方が合法である理由:** AD-8 は「連続作業時間・猶予・腐敗判定のいずれの計時もコア内で行う」としか言っていない。A も B もコア内で計時している。B はむしろ「一貫性の規約」の時刻表現に忠実であり、AD-5 の「異常終了した場合、最後に完了した切り替えの状態に復帰する」を満たすには永続化された時刻が要るため、B が自然な実装である。A は §8 の「待機時 CPU 1% 未満」に忠実であろうとした結果である。

**合成が壊れる形:** ノート PC の常駐アプリである。金曜 17:00 に 20 分作業した状態で蓋を閉じ、月曜 09:00 に開く。A は 20 分と答え、B は 64 時間と答える。B では**蓋を開けた瞬間に必ず休息介入が発火する** — 毎朝、毎昼休み後、毎回。しかも AD-6 により非活性パネルであり、AD-7 により応答するまで消えず、FR-15 により「単純な無視によって解消されない」。休息介入が「開くたびに出るノイズ」になれば、PRD §4.6 が名指しした失敗様式 (「静かな通知は反射的に無視される」) をツール自身が再現する。逆に A では、スリープからの復帰後に閾値超過の判定が遅延する (`tokio::time::sleep_until` がスリープ中に進まない実装と組めば、50 分の deadline がスリープ時間分だけ後ろにずれる)。

**閉じ方 (新 AD 案):** 「AD-8a — 連続作業時間の時計源は壁時計 (UTC) とし、**システムスリープおよびプロセス不在の時間は連続作業時間に算入しない。** コアはスリープ/ウェイク通知 (`NSWorkspaceWillSleepNotification` / `didWake`) をアダプタ経由でポートとして受け取り、スリープ区間を計数から除外する。除外の実装はコア側の区間演算であり、アダプタは通知の中継のみを行う。」— スリープ通知は OS API であるため AD-1 によりアダプタ必須である点も同時に明記する必要がある (現在の `adapters/` 一覧にスリープ通知の受け口はない)。

### DP-02 [Critical] 連続作業時間のリセット契機 — 切り替え or 活性化

- **Unit A — `domain/switch.rs`:** PRD §6.3 の縮退仕様「**連続作業時間**は『直近に宣言された**切り替え**からの経過時間』で代替する」を字義どおり実装し、`Switch` のコミットごとに連続作業時間を 0 に戻す。
- **Unit B — `domain/rest.rs`:** PRD §3 用語集の「直近に**現在地**が**活性**となった時点からの経過時間」を実装し、非活性→活性の遷移でのみ 0 に戻す。活性状態のままステップを移っても継続して計数する。

**両方が合法である理由:** AD-8 はどちらの定義も禁じていない。PRD 自身が §3 と §6.3 で二つの定義を与えており、スパインはどちらを採るか書いていない。AD-10 の識別子表にも `ContinuousWorkTime` があるだけで、リセット契機は語彙の対象外である。

**合成が壊れる形:** 45 分ごとに切り替えを宣言するユーザー — つまり本ツールの理想的な利用者 — に対し、**A は休息介入を一度も発火させない。** 閾値 50 分に達する前に毎回リセットされるからである。v1 の唯一の能動機能が、最も熱心なユーザーに対してだけ沈黙する。B では正しく発火するが、B は §6.3 の縮退仕様の文言に反しているため、レビューで「PRD どおりに直せ」と指摘されて A に戻される。さらに A と B が別々のモジュールで別々に実装されると (`switch.rs` が 0 を書き、`rest.rs` が活性遷移でしか 0 を書かない)、リセットが二系統になり、休息から戻って即座に切り替えた場合に二重リセットされる。

**閉じ方:** 「AD-8b — 連続作業時間は**現在地が非活性から活性へ遷移した時点**を起点とする。同一の活性区間内での切り替えは起点を更新しない。」と一文で固定し、PRD §6.3 の文言との差分を明示的に記録する (縮退仕様が言う「切り替え」は「休息からの復帰」を含意していたと解釈する、あるいは PRD を直す)。

### DP-19 [Medium] 起動時の連続作業時間の初期値

- **Unit A:** プロセス起動時に連続作業時間を 0 から始める。AD-5 は「最後に完了した切り替えの状態に復帰する」としか言っておらず、連続作業時間は切り替えの状態ではない。
- **Unit B:** DP-01 の B と同じく `last_activated_at` から復元する。

**壊れる形:** A ではクラッシュ再起動 (あるいはログイン時の自動起動 FR-3) のたびに休息タイマーが 0 に戻る。開発中に何度も再起動するユーザーは休息介入を一度も見ない。B では朝の起動直後に必ず介入が出る (DP-01 と同根)。AD-5 の復帰対象に「現在地・中断メモ」しか挙がっていないことが原因であり、**連続作業時間はクラッシュ復帰の対象なのか否かが未定である。**

**閉じ方:** AD-5 の復帰対象を列挙で確定する。「復帰対象は現在地・中断メモ・現在地の活性状態・連続作業時間の起点の四つとする。介入の表示状態と一時ホットキーの登録は復帰対象に含めず、起動時に必ず未表示・未登録から始める」。後半は DP-05 と接続する。

## クラスタ B — 所有者の欠落 (AD-2)

AD-2 の Rule は逐語的には次の三文である。「Svelte 側は状態を保持しない」「画面に出す値はすべてコアから受け取った直後の写し」「**現在地を変更しうるコードパスはコア内に一つだけ存在する**」。最後の一文が拘束するのは `CurrentPosition` だけであり、v1 に実在する他の可変状態には所有者規定が及んでいない。

### DP-03 [Critical] 活性/非活性の所有者が存在しない

PRD §3 は現在地に「**活性**と**非活性**の二状態」を与えている。スパインの「構造の種」も「休息中は値を保持したまま非活性となる」と書いている。しかし **ERD の `CURRENT_POSITION` に状態フィールドはなく、AD-10 の識別子表に「活性」「非活性」の語は存在しない。**

- **Unit A — `domain/position.rs`:** `CurrentPosition { step_id: Uuid, state: PositionState }`, `enum PositionState { Active, Inactive }`。活性/非活性は現在地の属性であり、AD-2 の「現在地を変更しうるコードパスはコア内に一つだけ」に従って `switch_current_position` と同じ一箇所で変更する。
- **Unit B — `domain/rest.rs`:** AD-10 の表にある `Rest` を実体として起こし、`Rest { started_at, ended_at: Option<...> }` を SQLite に持つ。活性か否かは「未終了の `Rest` 行が存在するか」で導出する。現在地そのものは一切変更しないため AD-2 の単一コードパス規定に抵触しない。

**両方が合法である理由:** A は `PositionState` / `Active` / `Inactive` という**識別子表にない語**を導入するため、AD-10 の「表にない語をドメインに導入する場合は、PRD §3 用語集への追加と本表への追加を同時に行う」に従えば表を直さねばならない。B は表にある `Rest` しか使わないため AD-10 に完全適合する。つまり **AD-10 は B を優遇し、ERD は A を示唆し、AD-2 の単一コードパス規定は A を要求する。** どの AD も勝たない。

**合成が壊れる形:** A と B が両方書かれた場合 (休息介入を担当するストーリーが B を、切り替えを担当するストーリーが A を実装する — これは自然な分割である)、「休んでいるか」の真実が二箇所になる。休息中に切り替えを宣言すると、A の経路は `state = Active` を書き、B の `Rest` 行は開いたままになる。連続作業時間は DP-02 のどちらの定義でも壊れる。FR-6 の「現在地の一意性」は守られたまま、**「一つの現在地が同時に活性かつ休息中」** という状態が成立する。これは FR-6 が守ろうとしたものの実質的な破壊である。

**閉じ方:** 「AD-2a — 現在地は `(step_id, activity)` の対であり、`activity` は `CurrentPositionActivity { Active, Inactive }` とする。休息は独立した実体ではなく、現在地が `Inactive` である区間を指す語である。`Rest` を行として持たない。」+ AD-10 の表に `活性 → Active` / `非活性 → Inactive` を追加。加えて ERD の `CURRENT_POSITION` にフィールドを明示する。

### DP-09 [High] 中断メモの下書きは誰が持つか — AD-2 と AD-5 の正面衝突

AD-5: 「入力途中のメモは永続化しない」。AD-2: 「Svelte 側は状態を保持しない。画面に出す値はすべてコアから受け取った直後の写しであり」。中断メモのテキストエリアはこの二つの中間にあり、どちらの規則も逃げ道を与えている。

- **Unit A — `src/overlay/NoteEditor.svelte`:** `let draft = $state('')` でローカルに保持し、確定時に `commit_switch(note)` を一度だけ呼ぶ。AD-5 に完全適合 (下書きはどこにも永続化されない)。AD-2 の「状態を保持しない」には反するが、AD-2 の Rule の拘束対象は現在地であり、下書きは現在地ではない。
- **Unit B — `commands/note.rs` + `domain/draft.rs`:** AD-2 を字義どおり守り、打鍵ごとに `update_interruption_note_draft` コマンドを送る。コアはメモリ上に下書きを保持し (永続化しないため AD-5 適合)、`interruption_note_draft_changed` イベントで値を返し、Svelte は受け取った値を描画するだけにする。命名も「一貫性の規約」の `動詞_名詞` / `名詞_過去分詞` に適合する。

**合成が壊れる形:** B は日本語入力で破綻する。中断メモは日本語で書かれ、IME の変換中バッファを保持したテキストエリアに対して、IPC を往復した値を毎打鍵で再設定すれば composition が壊れる。加えて FR-7 の「5 打鍵以内で完了する」と FR-1 の 300ms 予算に対して、打鍵ごとの IPC 往復は測定対象そのものである。A は動くが、A が動く限り「オーバーレイは状態を持たない」という AD-2 の主張は虚偽になり、後続のストーリーが「下書きもコアにあるはず」という前提で書かれると噛み合わない。具体的には、DP-12 の「介入表示中にオーバーレイを開いて入力途中の状態」でクラッシュした場合、A では下書きは消え (FR-3 が許容)、B ではコアのメモリごと消える — ここは一致するが、**再表示時の復元**で割れる。B の実装者は「コアが持っているのだから閉じて開いても復元されるべき」と考え、A の実装者は「オーバーレイを閉じたら破棄」と考える。FR-19 が開示面について「閉じた時点で破棄」と明示しているのに、中断メモの下書きについては何も書かれていない。

**閉じ方:** AD-2 の Rule に例外を明記する。「AD-2b — **未確定の入力バッファ (中断メモの下書き) は提示面がローカルに保持してよい唯一の可変値である。** コアへ渡るのは確定時の一度のみであり、オーバーレイを閉じた時点で破棄される。これ以外のいかなる値も提示面は保持しない。」

### DP-11 [High] 事前生成ウィンドウの表示時、内容は再取得するか

スパインの起動シーケンスは「ウィンドウを生成し隠す」「以降ホットキーは表示の切替のみ」と固定した。ここで隠れているウィンドウの DOM が保持する内容の扱いが未定である。

- **Unit A:** 隠す際に DOM を保持する。最後に受け取った `current_position_changed` イベントの内容がそのまま残っており、表示は即座 (FR-1 の 300ms に余裕で適合)。AD-2 適合 — 表示している値は「コアから受け取った直後の写し」だったものである。
- **Unit B:** 隠す際に内容をクリアし、表示時に `get_current_position` コマンドで取り直してから描画する。AD-2 の「直後の写し」をより厳密に守る。

**合成が壊れる形:** A は古い値を表示する窓を持つ。介入パネル経由で現在地が非活性になった (DP-03) 場合や、休息から復帰した場合、オーバーレイに向けてイベントが飛んでいなければ (あるいは隠れた窓のリスナが外されていれば)、ホットキーを押した瞬間に**数時間前の現在地が表示される。** FR-8 の「再開時の位置提示」が、まさに再開の瞬間に嘘をつく。B は正しいが、IPC 往復 + 再描画が 300ms 予算に載り、かつ一瞬空の窓が見える — FR-1 の「入力受付開始まで 300ms」を満たすかは実装次第で、A の実装者と B の実装者は同じ受け入れ条件に対して別の計測結果を出す。**AD-2 には鮮度 (staleness) と無効化の規定がない。**

**閉じ方:** 「AD-3a — 提示面は表示 (show) の直前に必ずコアへ状態を要求し、応答を描画してから可視化する。隠れている提示面はイベントを購読しない。コアは提示面の表示要求に対して完全な表示用モデルを一度に返す。」+ 300ms 予算の内訳をこの往復を含めて定義する。

## クラスタ C — AD-7 の一時ホットキー

AD-7 の Rule は三文しかない。「介入の表示中のみ、二つの選択肢に対応するグローバルホットキーを登録する」「応答後ただちに解除する」「登録が残存したまま介入が消える経路を作ってはならない」。**介入が一つしか表示されないという前提が暗黙に置かれており、登録集合の所有者・キーの選び方・登録失敗時の振る舞いのいずれも規定されていない。**

### DP-04 [Critical] 介入が二つ同時に表示されたときのホットキー登録集合

- **Unit A — `domain/rest.rs` + `adapters/hotkey/intervention.rs` (FR-15, v1):** 休息介入の表示時に `Cmd+Opt+1` (休息に入る) / `Cmd+Opt+2` (猶予後に再提示) を登録する。応答時に両方を解除する。
- **Unit B — `domain/crossing.rs` (FR-14, v2):** スパインの「先送り」が「AD-6 と AD-7 が提示面と応答経路を既に固定しているため、v2 で追加するのは判定ロジックのみで足りる」と明言している。したがって B の実装者は同じ AD-7 に従い、二択に `Cmd+Opt+1` (完了させてから移行) / `Cmd+Opt+2` (ここで切り替え) を登録する。

**両方が合法である理由:** AD-7 は「二つの選択肢に対応するグローバルホットキーを登録する」としか書かず、キーの選定にも、同時に複数の介入が表示されうるかにも触れていない。スパイン自身が v2 で「判定ロジックのみ」と保証している。

**合成が壊れる形:** 交差介入が表示中に休息の閾値を超える。これは頻繁に起きる — 交差は本日計画の移行期待時刻で決まり、休息は連続作業時間で決まる独立事象であり、FR-14 は「選択されるまで介入は消えない」ため交差介入は長時間表示されうる。このとき:

1. `tauri-plugin-global-shortcut` の `register()` は既登録のショートカットに対して `Err(AlreadyRegistered)` を返す。B の実装者は AD-7 に失敗経路がないため、これを「一貫性の規約」の「ユーザー操作を伴わない失敗はログのみ」に流す。結果、**二つ目の介入は応答手段を一切持たずに表示される。** 非活性パネルであるためキーボードは届かず (AD-6)、FR-15 により消えない。
2. 仮に登録が成功 (置き換え) した場合、先に出ていた交差介入のホットキーが黙って休息介入のハンドラに繋がる。ユーザーは交差介入を見ながら `Cmd+Opt+1` を押し、**休息に入る。**
3. 休息に先に応答した場合、AD-7 の「応答後ただちに解除する」を A が字義どおり実行し、まだ表示中の交差介入のキーまで解除する。

**閉じ方:** 「AD-7a — 介入は同時に一つしか表示しない。表示中に別の契機が成立した場合は待ち行列に入れ、先行する介入の応答後に表示する。待ち行列は最大 1 件とし、同一契機の重複はマージする。」加えて「AD-7b — 一時ホットキーの登録/解除は `adapters/hotkey/` の単一のレジストリ型が排他的に所有する。介入モジュールはレジストリに対して『この介入の応答キーを有効化/無効化する』としか要求できない。」

### DP-05 [Critical] 介入の解除義務に所有者がいない

AD-7 の第三文は禁止 (「登録が残存したまま介入が消える経路を作ってはならない」) であって、**義務の割り当てではない。** 「介入が消える」経路は複数ある。

- **Unit A — `domain/intervention.rs`:** 自分のハンドラ (ホットキー応答) の中でのみ解除する。これは AD-7 に完全適合している — A は残存する経路を「作っていない」。
- **Unit B — `commands/switch.rs`:** ユーザーが介入表示中にオーバーレイを開いて切り替えを宣言し、連続作業時間がリセットされた (DP-02 の A 定義) ため、休息介入の成立条件が消えた。B はパネルを隠すコマンドを発行する。B も AD-7 に適合している — B はホットキーを「登録していない」ので残存させようがない、と B の実装者は考える。

**合成が壊れる形:** B の経路でパネルが消え、A のハンドラは呼ばれず、`Cmd+Opt+1` / `Cmd+Opt+2` が**グローバルに登録されたまま残る。** 以後、ユーザーが他アプリでその組み合わせを押すと、消えた介入のハンドラが発火して現在地が非活性になる (= 気づかないうちに休息に入る)。AD-7 が名指しで禁じた状態が、AD-7 を両方守った二つのユニットの合成から生まれる。同じ穴はアプリ終了 (FR-3 の「明示的な終了操作」) と、DP-19 のクラッシュ再起動にも開いている。

**閉じ方:** DP-04 の AD-7b と同じレジストリ所有に加えて、「介入パネルの可視性と一時ホットキーの登録は**同一の状態機械の同一の遷移でしか変化しない。** パネルを隠す経路は介入の応答経路ただ一つとする (条件消滅による自動消去を作らない — 消滅させたい場合は『条件解消』という第三の応答として定義し、同じ遷移を通す)。」

### DP-06 [Critical] ホットキー登録の失敗経路が定義されていない

ユーザーが他アプリ (Raycast, Alfred, IME, Xcode) に束縛済みの組み合わせを、AD-7 の一時ホットキーが要求した場合、`register()` は失敗する。AD-7 には失敗時の規定がない。

- **Unit A:** 「一貫性の規約」の「ユーザー操作を伴わない失敗 (計時・永続化) はログのみで、介入としては提示しない」に従い、ログを書いてパネルを表示する。
- **Unit B:** 応答不能な介入を出すべきではないと判断し、介入の発火を見送る (ログのみ)。

**合成が壊れる形:** A の結果は「キーボードで応答できず、AD-6 により入力先も奪わず、FR-15 により消えないパネル」である。マウスクリックは非活性パネルでも届くため完全な詰みではないが、AD-7 の Prevents 節が名指しで防ごうとした「介入の二択がマウス操作を強制すること」がそのまま起きる。B の結果は「休息介入が恒久的に沈黙する」であり、v1 唯一の能動機能が、ユーザーに何も告げずに無効化される。FR-11 には「OS 権限が未付与の場合、ツールは本機能を無効化した状態で他機能を継続動作させ、**その旨をユーザーに示す**」という縮退規定があるのに、AD-7 の失敗には対応する規定がない。

**閉じ方:** 「AD-7c — 一時ホットキーの登録に失敗した場合、介入はパネル上に応答手段 (クリック可能な二択) を必ず併せ持つ。ホットキーは加速手段であって唯一の応答経路ではない。登録失敗は起動時に一度検出してユーザーに提示し、設定でキーを変更できる。」— これは同時に FR-7 の「5 打鍵以内」と同水準の受け入れ条件を介入側にも与えることになる。

### DP-14 [High] 一時ホットキーのキー形状に制約がない

- **Unit A:** FR-7 の「5 打鍵以内で完了する」の精神と AD-7 の「手をホームポジションから動かさずに済む」(memlog の decision) を最大化し、修飾キーなしの `1` / `2` を登録する。
- **Unit B:** `Cmd+Opt+1` / `Cmd+Opt+2` を登録する。

**合成が壊れる形:** グローバルショートカットはフォーカスに関係なく発火する。A のキーでは、介入が表示されている間にユーザーがオーバーレイ (AD-6 によりフォーカスを取る通常ウィンドウ) で中断メモに「1 件目の確認待ち」と入力しようとした瞬間、`1` が介入への応答として食われる。中断メモには何も入らず、ユーザーは気づかないまま休息に入る。他アプリでの通常のタイピングも同様に壊れる。これは PRD §7.2 の「他アプリケーションの操作を奪って不可逆な結果を招いてはならない」の直接違反であるが、**AD-7 も AD-6 も A を禁じていない。**

**さらに悪い変種:** AD-7 の一時ホットキーが FR-1 のオーバーレイ呼び出しホットキーと衝突する場合。AD-11 は「休息閾値・猶予・腐敗判定期間**を含む**ユーザー設定は SQLite の設定テーブルに置く」と書いており、呼び出しホットキーも設定に含まれうる。ユーザーが FR-1 のホットキーを `Cmd+Opt+1` に変更した瞬間、介入表示中はオーバーレイを開けなくなるか、介入に応答できなくなる。どちらが起きるかは登録順に依存し、登録順を定めた AD はない。

**閉じ方:** 「AD-7d — 一時ホットキーは修飾キーを 2 個以上含む組み合わせに限る。FR-1 の呼び出しホットキーと同一の組み合わせは登録前に検査して拒否する。両者の予約集合はコアが所有し、設定変更時に衝突検査を行う。」

## クラスタ D — 順序と生存期間

### DP-07 [Critical] 切り替えトランザクション中に介入応答が割り込む

`tauri-plugin-global-shortcut` のコールバックは Tauri command のハンドラとは別スレッドで走る。AD-5 の「単一のトランザクション」は DB の原子性を保証するが、**コア内のメモリ状態に対する排他は規定されていない。**

- **Unit A — `domain/mod.rs`:** コア全体を `Mutex<Domain>` で一つに包む。介入ホットキーのコールバックは切り替えトランザクションの完了まで待つ。
- **Unit B — `domain/mod.rs`:** FR-1 の 300ms 予算と §8 の応答性を守るため、集約ごとに錠を分ける (`Mutex<CurrentPosition>`, `Mutex<RestState>`)。

**両方が合法である理由:** AD-2 の「現在地を変更しうるコードパスはコア内に一つだけ存在する」は B でも守られている — 現在地を変更するのは `switch_current_position` ただ一つである。休息応答が変更するのは DP-03 の B モデルでは `Rest` 行であり、現在地ではない。AD-5 の「単一のトランザクション」も B で守られている。

**合成が壊れる形 (B で実際に起きる交錯):**

```
T1 (command スレッド): switch_current_position(step4)
  1. 読む: position = { step3, Active }
  2. BEGIN; INSERT note(step3); UPDATE position → step4;
T2 (hotkey スレッド):       休息応答「休息に入る」
  3. Rest 行を INSERT (started_at = now) / あるいは position.activity = Inactive
T1:
  4. COMMIT (position = { step4, Active })
```

結果: ユーザーは休息に入ったつもりで席を立ち、現在地は step4 の**活性**として残り、連続作業時間が回り続ける。50 分後に離席中のデスクトップに休息介入が積み上がり、DP-04 と合流する。A ではこれは起きないが、A はホットキー応答のレイテンシが DB 書き込みに支配される。

**閉じ方:** 「AD-5a — 現在地に関わる状態 (指すステップ・活性/非活性・連続作業時間の起点) は単一の集約であり、単一の錠で保護する。この集約に対する読み取りと書き込みは常に同一のクリティカルセクション内で行う。トランザクション境界はこのクリティカルセクションと一致させる。」

### DP-12 [High] 介入表示中にオーバーレイから切り替えを宣言した場合

- **Unit A — `domain/intervention.rs`:** FR-15 の「いずれかが選ばれるまで**介入**は消えず、単純な無視によって解消されない」を字義どおり守り、切り替えが起きても休息介入を出したままにする。
- **Unit B — `domain/rest.rs`:** DP-02 の A 定義で連続作業時間がリセットされたため介入の成立条件が消えたと判断し、パネルを隠す。

**合成が壊れる形:** A では、ユーザーが新しいステップに移った直後に「休息に入りますか」というパネルが残り、答えると**今まさに始めた作業が非活性になる。** B では FR-15 の「単純な無視によって解消されない」が破れる — 切り替えの宣言は介入への応答ではないのに介入が消えており、「無視すれば消える (別の操作をすれば消える)」という抜け道ができる。PRD §4.6 が防ごうとした「反射的に無視される介入」がまさにこの抜け道から復活する。加えて B は DP-05 の残存登録を生む。

**閉じ方:** DP-05 の AD-7 拡張と同じ。「条件解消」を第三の応答として明示的に定義し、それが起きうる契機を列挙する (切り替えの宣言・休息の開始・アプリ終了)。

### DP-13 [High] 介入パネルが描く現在地はスナップショットか追随か

- **Unit A — `src/intervention/`:** 介入発火時にコアから受け取った表示用モデルを描画し、以後更新しない。介入は「その時点の作業」についての問いだからである。AD-2 適合 (受け取った直後の写しである)。
- **Unit B — `src/intervention/`:** `current_position_changed` を購読して追随する。AD-2 適合 (常に直後の写しである)。

**合成が壊れる形:** ユーザーが介入表示中にオーバーレイで step3 → step4 に切り替える (DP-12)。A のパネルは step3 を表示したまま「休息に入る」を提示する。ユーザーは step3 の話だと思って応答するが、コアが非活性にするのは step4 である。**画面に見えている対象と、応答が作用する対象が異なる。** B では表示が step4 に変わるため対象は一致するが、今度は AD-6 の二面が同時に同じ値を描くことになり、DP-11 の鮮度問題と合わせて「オーバーレイは step4、パネルは step3」という**同時に二つの現在地が見える状態**が生じうる。FR-6 の一意性はモデルに対する不変条件であって提示に対するものではないため、どの AD もこれを禁じていない。

**閉じ方:** 「AD-3b — 介入への応答は、介入が発火した時点の現在地に対してではなく、応答時点の現在地に対して作用する。パネルは現在地を描かない (何の作業かを示さず、休息の可否のみを問う)、あるいは描くなら追随する。いずれかをスパインで固定する。」

### DP-18 [Medium] FR-5 のステップ分割はトランザクション境界の外にある

AD-5 のトランザクションは「**現在地の移動**と**中断メモの確定**」に限定されている。FR-5 のステップ分割は現在地を移動しない (「現在地は分割後の前半を指す」= 同じ作業単位を指し続ける) ため、AD-5 のトランザクションの対象外である。

- **Unit A — `domain/step.rs`:** 分割を一つのトランザクションで書く (新ステップ INSERT → 後続の連番再計算 UPDATE → 中断メモの帰属変更 UPDATE)。
- **Unit B — `adapters/storage/step.rs`:** 三つの独立した書き込みとして実行する。AD-5 の要求はこれを含んでいないため B は違反していない。

**合成が壊れる形:** B の途中でプロセスが落ちる。AD-5 の復帰規定は「最後に完了した**切り替え**の状態に復帰する」であり、**切り替えが起きていないので復帰対象がない。** 起動後、同じ連番 (No.3) を持つステップが二つ存在する DB、あるいは分割後の後半に中断メモが付いた DB が残る。FR-5 の三つの受け入れ条件はすべて破れている。FR-2 と FR-8 が要求する「第 N ステップ / 全 M ステップ」は二つの No.3 をどう数えるかで割れる。

**閉じ方:** AD-5 の Rule を一般化する。「AD-5b — **ドメイン不変条件を一時的に破る書き込みの並びは、例外なく単一のトランザクションに収める。** 対象は少なくとも次を含む: 現在地の移動と中断メモの確定 / ステップの挿入・分割に伴う連番の再計算と中断メモの帰属変更 / 現在地の活性状態の変更と連続作業時間の起点の更新。」

## クラスタ E — データ形状の衝突

### DP-08 [Critical] ステップの完了状態が存在しない

FR-13 は「現在地が指すステップが**未完了**であること」を交差判定の条件にし、FR-14 は「現在の**ステップを完了させて**から移行する」を選択肢にする。FR-6 は「新たなステップが現在地となった時点で、直前の現在地は自動的に解除される」と言うが、「解除」が「完了」なのかは書いていない。**ERD の `STEP` に完了フィールドはなく、AD-10 の識別子表に「完了」に相当する語がない。**

- **Unit A — `domain/step.rs`:** `Step { ..., completed_at: Option<DateTime<Utc>> }` を持つ。現在地が離れるときに明示的に「完了して離れる」「中断して離れる」を区別する (FR-7 の中断メモは後者にのみ付く)。
- **Unit B — `domain/step.rs`:** 完了フィールドを持たない。完了は「現在地がこのステップより後ろの連番にある」ことから導出する。AD-10 に語を追加せずに済むため B のほうが AD-10 に忠実である。

**合成が壊れる形:**

1. ユーザーが step5 まで進んだ後、step2 に戻る (FR-5 のステップ追記や、やり直しで頻繁に起きる)。A では step3〜5 は完了のまま。B では step3〜5 が**一斉に未完了に戻る。**
2. FR-5 でステップを挿入すると連番が再計算される。B では挿入位置以降の完了状態が全部ずれる。
3. FR-19 の開示面は「どこまで終わったか」を描く。A と B で描かれる絵が違う。
4. v2 の FR-13 (交差検出) は「現在地が指すステップが未完了」を条件にするが、B の定義では**現在地が指すステップは定義上つねに未完了**であり、条件が恒真になる。交差は「移行期待時刻の経過」だけで判定されることになり、FR-13 の二条件のうち一つが消える。

これは v1 スコープ (FR-6) で決まってしまい、v2 (FR-13/FR-14) で効いてくる型の分岐である。後から直すと現在地の移動経路全体を書き直すことになる。

**閉じ方:** AD-10 の表に `完了 → completed` (あるいは新しい用語を PRD §3 に追加) を入れ、「AD-10a — ステップは明示的な完了状態を持つ。現在地が離れることと、ステップが完了することは別の事実である (FR-7 の中断メモは未完了のまま離れた場合にのみ記録される)。」を追加する。**PRD §3 に「完了」の定義がないこと自体が上流の穴であり、PRD 側への差し戻しが要る。**

### DP-17 [High] ステップ順序の保持方式と、現在地の指し方

「一貫性の規約」は「ID は UUID v7 (生成順に単調増加し、**ステップ順序とは独立**)」と書き、ID と順序を明示的に切り離した。しかし**順序をどう保持するかは書いていない。**

- **Unit A:** `Step { ordinal: i32 }`。挿入・分割のたびに後続を UPDATE で振り直す (FR-4 の「No.1 から連番が振られる」を DB の真実として保持)。`CurrentPosition` は `step_id: Uuid` を持つ。
- **Unit B:** `Step { rank: f64 }` あるいは連結リスト。表示上の No. は読み取り時に計算する。`CurrentPosition` は `step_id: Uuid` を持つ。
- **Unit C:** `CurrentPosition { task_id: Uuid, step_no: i32 }` — ERD の `CURRENT_POSITION }o--|| STEP : "指す"` は「ステップを指す」としか言っておらず、(タスク, 連番) の組で指すことを禁じていない。

**合成が壊れる形:** C は FR-5 の受け入れ条件「ステップの追加により後続のステップの連番が再計算されても、**現在地は同一の作業単位を指し続ける**」を構造的に満たせない。No.3 の前にステップを挿入した瞬間、現在地が指す「No.3」は別の作業単位になる。A と B の間では、`ports/storage` のクエリ面が完全に別物になる (A は `ORDER BY ordinal` で済み、B は順序解決ロジックを持つ)、FR-2/FR-8 が要求する「第 N / 全 M」が A では読み出し、B では計算になる、そして DP-18 のトランザクション境界が A でのみ必要になる。

**閉じ方:** 「AD-10b — ステップの順序は `ordinal: i32` として保持し、挿入・分割・削除のたびに 1..N に再計算する (再計算は DP-18 のトランザクション内で行う)。**現在地はステップを ID で指す。連番で指してはならない。**」

### DP-15 [High] 設定テーブルのキー空間と単位に規約がない

ERD の `SETTING { string key; string value }` と AD-11 だけが規定であり、**キーの名前空間も値の符号化も未定である。** AD-10 の識別子表に `設定` / `Setting` の項目すらない。

- **Unit A — `domain/rest.rs`:** キー `rest_threshold_minutes`、値 `"50"` (PRD FR-15 の「既定値は 50 分」をそのまま写す)。
- **Unit B — 設定 UI を担当するストーリー:** 「一貫性の規約」の「**期間は秒の整数**」に従い、キー `rest.threshold`、値 `"3000"`。

**合成が壊れる形:** 二つのキーが別々に存在し、片方だけが書かれ、もう片方が読まれる。あるいは同じキーに分と秒が混在する。50 秒ごとに休息介入が出るか、50 時間出ないかのどちらかになり、しかも DB を見るまで原因が分からない。AD-11 の Prevents (「設定ファイルと DB に状態が分かれ、AD-2 の『所有者は一つ』が崩れること」) は DB の**内部で**同じことが起きる可能性を塞いでいない。

**閉じ方:** 「AD-11a — 設定キーはコア内の列挙型 (`SettingKey`) が唯一の正であり、文字列リテラルを設定アクセスに使わない。値の符号化は『一貫性の規約』に従い、期間はすべて秒の整数とする。UI に表示する単位への変換は提示層で行う。」+ AD-10 の表に `設定 → Setting` を追加。

### DP-16 [High] 既定値の seed 有無で「既定値」の意味が変わる

AD-11 は「既定値はコード内に定数として持ち、DB に値がない場合のフォールバックとする」と書いている。

- **Unit A — `adapters/storage/migrations.rs`:** 初回起動時に設定テーブルへ既定値を INSERT する (マイグレーションの一部として。設定画面が常に値を持つほうが実装が単純)。
- **Unit B — `domain/settings.rs`:** DB に行がなければ定数を返すだけで、書き込まない (AD-11 の「フォールバック」を字義どおり)。

**合成が壊れる形:** A では、次のビルドでコード内の既定値を 50 分から 45 分に変えても**ユーザーの環境では永久に 50 分のまま**である。初回起動時に seed された行が勝つからである。ユーザー (= 作者本人) は「定数を直したのに変わらない」に遭遇し、DB を覗くまで理由が分からない。さらに A と B が混在すると、「設定をリセットする」の意味が「行を消す」(B では定数に戻る、A では次回起動で再 seed される) で割れる。

**閉じ方:** AD-11 に一文追加。「**既定値を DB に seed しない。** DB の行はユーザーが明示的に変更した値のみを表す。行の削除は既定値への復帰を意味する。」

## クラスタ F — 用語と構造の穴

### DP-20 [Medium] `Reentry` に契機の定義がない

`再入 → Reentry` は AD-10 の識別子表にあるが、**ERD に現れず、どの AD の Rule にも現れず、どのコマンド/イベントにも対応しない。** PRD §3 の定義は「中断された**ステップ**が再び**現在地**となり、作業が再開されること」。

- **Unit A:** `Reentry` = 「中断メモを持つステップが現在地になった」。`reentry_occurred { note }` を発行し、オーバーレイが中断メモを提示する (FR-7 の「記録された中断メモは、当該ステップが再び現在地となったときに自動的に提示される」)。
- **Unit B:** `Reentry` = 「過去に現在地であったステップが再び現在地になった」(中断メモの有無を問わない)。
- **Unit C:** `Reentry` = 「休息が終了して現在地が活性に戻った」(FR-15 の「終了時に現在地は活性へ戻り、**FR-8 と同じ形式で提示される**」)。

**合成が壊れる形:** A の実装では、休息から復帰したときに何も提示されない (現在地は変わっていないので `Reentry` が発火しない) — FR-15 の最後から二番目の受け入れ条件が落ちる。C の実装では、通常の切り替えで戻ったときに提示されない — FR-7 の受け入れ条件が落ちる。B は両方を取りこぼす。**三つとも AD-10 に適合しており、三つとも別の FR を落とす。**

**閉じ方:** 「AD-10c — `Reentry` は次の二つの契機で発火するコアのイベントである: (a) 現在地が別のステップへ移動し、移動先が過去に現在地であった、または中断メモを持つ場合 (b) 現在地が非活性から活性へ戻った場合。いずれの場合も提示内容は同一 (タスク内の位置 + 中断メモ) とする。」

### DP-21 [Medium / v2 で致命] v1 の観測ポートは休息計時の経路に入るのか

AD-9: 「v1 では**宣言由来の入力のみを供給する実装**を置き、v2 でアクティブウィンドウ観測の実装に差し替える。コアは入力の出所を区別しない」。

- **Unit A — `adapters/observation/declared.rs`:** 切り替えの宣言ごとに `WorkContext` を合成して `ObservationPort` に流す。連続作業時間はこのポート経由の入力で駆動する。v2 で `nsworkspace.rs` に差し替えれば、コアを触らずに FR-15 が「実際の作業」ベースになる。
- **Unit B — `adapters/observation/noop.rs`:** ポートは定義するが何も流さない (アクティブウィンドウを観測しない以上、供給できる `WorkContext` は存在しない)。連続作業時間は `Switch` コマンドから直接駆動する。

**両方が合法である理由:** AD-9 の Rule は「実装を置く」としか言っておらず、**その実装が何を供給するかも、コアのどの機能がポートを経由するかも規定していない。**

**合成が壊れる形:** B は AD-9 の Rule に完全適合しながら、AD-9 の Prevents (「v1 を『観測が存在しない』前提で書き、v2 でドメインロジックの書き直しが必要になること」) をそのまま実現する。v2 で NSWorkspace 実装を挿しても、連続作業時間は依然 `Switch` から駆動されており、§6.3 の縮退 (「切り替えを宣言せずに離席した場合、作業継続中とみなされ介入が誤発火する」) が v2 でも解消されない。**AD-9 は防ぎたい事態を防いでいない。**

**さらに:** A は `WorkContext` (= 「最前面のアプリケーション名とウィンドウタイトルの組」, PRD §3) に、宣言由来のステップ名を詰め込むことになる。アプリ名もウィンドウタイトルも存在しないからである。これは型に嘘を書く行為であり、真面目な実装者は `enum ObservationInput { Declared { step_id }, Observed { app, title } }` を選ぶ — が、それは AD-9 の「コアは入力の出所を区別しない」の明確な違反である。**AD-9 は、正直な型を禁じている。**

**閉じ方:** AD-9 の Rule を具体化する。「v1 の宣言由来実装は、切り替えの宣言ごとに `WorkContext` を供給する。連続作業時間の計数は例外なくこのポートからの入力で駆動し、`Switch` コマンドから直接駆動しない。`WorkContext` は `{ source_opaque_id, label }` の形とし、v1 は `label = ステップ名`、v2 は `label = アプリ名 + ウィンドウタイトル` を入れる — コアは `label` の意味を解釈せず、同一性の比較のみを行う。」

### DP-22 [Medium] `adapters/presentation/` がソースツリーに存在しない

スパイン内部の三箇所が食い違っている。

1. mermaid 図: アダプタ層に `PR["presentation<br/>FR-2 / FR-7 / FR-15 / FR-19"]` がある。
2. 層の表とソースツリー: `ports/` の説明に「(storage, observation, presentation)」とある。
3. **ソースツリーの `adapters/` には `hotkey/` `autostart/` `storage/` `observation/` の四つしかなく、`presentation/` がない。**

**具体的な分岐:** FR-1 の受け入れ条件「呼び出し前に最前面であったアプリケーションは、オーバーレイを閉じた時点でフォーカスを回復する」を実装する場所。

- **Unit A — `adapters/hotkey/`:** ホットキー発火時に `NSWorkspace.frontmostApplication` を捕まえ、閉じるときに `activate` する。ホットキーが契機なのだから同じアダプタに置く。AD-1 適合。
- **Unit B — `adapters/presentation/` を新設:** 図と ports の記述に従って作る。AD-1 適合。
- **Unit C — `src/overlay/`:** Svelte から `getCurrentWindow().hide()` と Tauri のウィンドウ API で処理する。AD-1 の Rule は「OS API の呼び出しは `adapters/` 配下にのみ存在してよい。`domain/` は OS API・Tauri API・Web API のいずれも参照しない」— 第二文は `domain/` のみを拘束しており、`src/` (Svelte) が Tauri のウィンドウ API を呼ぶことを第一文がどこまで禁じているかは読みが割れる。実際、FR-1 の Esc で閉じる処理は Svelte 側のキーハンドラから呼ぶのが最も自然である。

**合成が壊れる形:** 三つのユニットが三箇所にウィンドウ制御を書き、「隠す」経路が三つできる。DP-11 (表示時の再取得) と DP-05 (介入の解除) はいずれも「隠す」経路に義務を紐づけているため、経路が三つあれば義務は三つとも取りこぼされる。加えて、DP-12 の「介入表示中にオーバーレイを開いて閉じた」場合、「呼び出し前に最前面であったアプリケーション」を誰がいつ捕まえ直すのかが未定である (介入パネルは非活性なので frontmost を変えないが、オーバーレイは変える)。

**閉じ方:** ソースツリーに `adapters/presentation/` を追加し、「AD-6a — ウィンドウの生成・表示・非表示・フォーカス復帰は `adapters/presentation/` が排他的に所有する。Svelte 側は Tauri のウィンドウ API を直接呼ばず、`hide_overlay` などのコマンドを通す。」を追加する。合わせて mermaid 図・ports の記述・ソースツリーの三者を一致させる。

### DP-10 [High] イベントのペイロード形状 — fat event か id 通知か

AD-3 は「コア → Svelte は Tauri event のみ」とし、「一貫性の規約」は event 名を `名詞_過去分詞` と定めた。**ペイロードの形状は未定である。**

- **Unit A:** `current_position_changed` に表示用モデル全体を載せる (`{ task_name, step_index, step_total, step_body, note, continuous_work_time_sec }`)。提示面は受け取って描くだけになり、AD-2 の「直後の写し」に最も忠実。
- **Unit B:** イベントは通知のみ (`{ position_id }`) とし、提示面が `get_current_position` コマンドで取りに行く。AD-3 の「戻り値は結果であって状態の所有権ではない」に適合。

**合成が壊れる形:** A で書かれたオーバーレイと B で書かれた介入パネルは、コアに対して別々の API 面を要求する。B の経路には「イベントとクエリの間の窓」があり、その間に別の変更が起きると提示面は新しい ID に対して古い状態を描く — AD-3 も AD-2 も順序保証を書いていない。さらに A には副作用がある: Tauri の `emit` は既定で**全ウィンドウに配信される。** A のイベントは中断メモ本文を載せているため、介入パネル (中断メモを表示すべきでない面) にもメモ本文が届く。AD-12 が守るのはネットワーク境界だけで、**ウィンドウ間の配信範囲を制約する AD はない。** 「一貫性の規約」のログ規定が「中断メモ本文をログに書かない」と明記しているのに、イベントの宛先には同等の規定がない。

**閉じ方:** 「AD-3c — イベントは完全な表示用モデルを載せる。イベントは宛先ウィンドウを明示して送る (`emit_to`)。介入パネル宛のイベントに中断メモ本文を含めない。」

## 付録 — AD-10 の識別子表に存在しないドメイン概念

AD-10 の Rule は「表にない語をドメインに導入する場合は、PRD §3 用語集への追加と本表への追加を同時に行う」と定めている。以下は**スパイン本文・ERD・PRD の受け入れ条件がすでに使っているのに表にない語**であり、それぞれが DP のどれかの根になっている。

| 概念 | 出典 | 表にないことの帰結 | 関連 DP |
| --- | --- | --- | --- |
| 活性 / 非活性 | PRD §3 現在地の定義、スパイン「構造の種」 | 状態の置き場所が二通りに割れる | DP-03 |
| 完了 (ステップの) | FR-13「未完了であること」、FR-14「完了させてから」 | 完了状態が存在しない設計が合法になる | DP-08 |
| 開示面 | FR-19、スパイン「能力 → アーキテクチャ対応」 | `DisclosureSurface` / `TaskListView` / `Overview` に割れる。開閉状態の所有者も未定 | DP-11 |
| 設定 (Setting) | ERD の `SETTING`、AD-11 | キー空間と単位の規約がない | DP-15, DP-16 |
| 閾値 | FR-15「閾値の既定値は 50 分」 | `rest_threshold` / `ContinuousWorkTimeLimit` に割れる | DP-15 |
| 介入の選択肢 / 応答 | AD-7 の全文が「二つの選択肢」に依存 | `InterventionChoice` / `InterventionResponse` / `RestChoice` に割れ、FR-14 と FR-15 で別型になる | DP-04 |
| 未着手 | PRD §3「値を持たない状態は未着手時のみ」、スパイン「構造の種」 | `CurrentPosition` が `Option` なのか専用の状態なのかが割れる | DP-03 |
| 移行期待時刻 | FR-9、FR-13 の交差判定条件 | v2。スパインの「先送り」は「時間配分の保持形式」のみを先送りしており、この語は先送り対象に入っていない | DP-08 |
| 常駐プロセスの終了 | FR-3「明示的な終了操作があるまで」 | 終了時に介入とホットキー登録をどうするかの所有者がいない | DP-05, DP-19 |

`Reentry`・`NextAction`・`Drift`・`Fixation` は逆の問題を持つ。**表にはあるが、ERD にも AD の Rule にも現れず、何がそれを生み・誰が所有するかが一切定義されていない。** `Reentry` は DP-20 のとおり v1 スコープで実害がある。

## 優先して閉じるべき五つ

コストと影響の比で並べると、次の五つが最初である。いずれも既存 AD への一〜二文の追記で閉じる。

1. **AD-2 の拘束範囲を現在地から全ドメイン状態へ広げる** (DP-03, DP-07, DP-09, DP-13 を同時に閉じる)。現在地・活性状態・連続作業時間の起点を一つの集約として定義し、単一の錠と単一のコードパスを与える。
2. **AD-8 に時計源とリセット契機を書く** (DP-01, DP-02, DP-19)。壁時計 + スリープ区間の除外 + 「非活性→活性」を起点とする、の三点。
3. **AD-7 にレジストリの所有者と単一表示の制約と失敗経路を書く** (DP-04, DP-05, DP-06, DP-12, DP-14)。AD-7 は現状、v1 唯一の能動機能の応答経路を、所有者なしの禁止事項だけで支えている。
4. **AD-10 の表にステップの完了状態と活性/非活性を追加する** (DP-03, DP-08)。PRD §3 に「完了」の定義がないため、PRD 側への差し戻しが要る。v1 で型が決まり v2 で効くため、後から直すコストが最も大きい。
5. **AD-5 のトランザクション規定を「不変条件を破る書き込みの並び」一般へ広げる** (DP-18, DP-07)。現在の規定は切り替えのみを守っており、FR-5 のステップ分割はクラッシュに対して無防備である。

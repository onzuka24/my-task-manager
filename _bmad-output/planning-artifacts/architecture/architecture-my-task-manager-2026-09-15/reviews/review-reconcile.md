# 照合レビュー — PRD が spine に着地しなかった点

## 判定の前提

- spine は v1 (FR-1..FR-8, FR-15, FR-19) を支えれば足り、v2 を設計する義務はない。v2 の記述が薄いことは指摘対象としない。**v2 を将来不可能にする、または PRD が v1 着手前に決めよと명示した事項を決めていない**場合のみ指摘する。
- 「builder が全 AD に従いながら PRD に反する成果物を作れるか」を各項の判定基準とする。AD に違反せずに違反できるなら、それは spine が落とした要求である。

## 1. v1 FR の「結果 (検証可能)」を満たす手段がない

### F-01 [重大] FR-1「閉じた時点で直前の最前面アプリがフォーカスを回復する」に手段がない

FR-1 の結果条件は三つあり、spine が扱っているのは 300ms のみである。「呼び出し前に最前面であったアプリケーションは、オーバーレイを閉じた時点でフォーカスを回復する」に対応する記述が spine のどこにもない。

AD-6 は「オーバーレイは通常ウィンドウとして実装し、フォーカスを取得してよい」とだけ述べる。macOS では通常ウィンドウを隠してもフォーカスは直前のアプリに戻るとは限らず、アプリ切替順序上の次のアプリに移る。直前アプリの記録と明示的な再アクティブ化、あるいはアプリの activation policy (`.accessory` / LSUIElement) の決定が要るが、spine は activation policy に一言も触れていない。これは §8 常時稼働の「常駐を利用者に意識させない」(Dock・アプリスイッチャへの出現可否) にも直結する未決である。

### F-02 [重大] FR-1「いかなるアプリケーションが最前面にあっても」がフルスクリーン時に成立しない

AD-6 はフルスクリーン対策を**介入パネル側にのみ**適用している (`NSWindowStyleMaskNonactivatingPanel`)。オーバーレイ側については「通常ウィンドウ」としか言っておらず、フルスクリーンアプリの前面に出るための window level / collection behavior (`.fullScreenAuxiliary`, `.canJoinAllSpaces`) の指定がない。通常ウィンドウのままでは、フルスクリーン作業中のホットキー押下は Space の切替アニメーション (約 0.5〜1 秒) を伴い、300ms の結果条件と「ツールを開くことが中断であってはならない」(§4.1 設計原則) の双方を破る。フルスクリーン作業は §7.2 が名指しした状況であり、v1 の主要な利用場面である。

### F-03 [重大] FR-2「二つ以上のタスク／ステップが同時に現れない」を構造的に保証していない

能力対応表は FR-2 を `src/overlay/` と AD-2/AD-3 に割り当てるが、AD-2/AD-3 が規定しているのは**状態の所有権**であって**画面に出る情報量**ではない。コアが送るイベントのペイロードに何が入ってよいかを縛る AD は存在しない。

したがって builder は、AD を一つも破らずに「コアから全タスク一覧を受け取り、初期表示では CSS で 1 件だけ見せる」実装を書ける。その状態でデバッグ表示・履歴ストリップ・「最近のタスク」が一つ足された瞬間に FR-2 と設計上の賭け #1 が壊れるが、どの AD にも違反しない。FR-2 を構造で守るなら「既定表示のイベントペイロードはステップ 1 件と位置情報 (N/M) のみを含み、一覧は開示面の専用コマンドでのみ取得できる」という不変条件が要る。それがない。

### F-04 [重大] FR-3 のクラッシュ耐性が「トランザクション」止まりで、OS 強制終了に耐える水準が未決

AD-5 は「単一のトランザクションで書き込む」と述べるが、§8 データ堅牢性が要求するのは「プロセスの異常終了**および OS の強制終了**をまたいで失われない」ことである。SQLite は WAL + `synchronous=NORMAL` ではコミット済みトランザクションが OS クラッシュ／電源断で失われうる。`journal_mode` と `synchronous` の決定 (最低でも切り替え確定の書き込みが fsync を伴うこと) が結果条件の成否を分けるが、spine は記憶方式 (SQLite) を選びながら耐久度を決めていない。addendum §3.2 は「記憶方式の選択そのものには制約を置いていない」が「書き込みのタイミングに対する制約である」と明言しており、spine はタイミングだけ批准して耐久度を素通りした。

加えて AD-5 の復帰対象は「最後に完了した切り替えの状態」に限定されている。PRD §3 の**現在地**は活性／非活性の二状態を持つ値であり、休息中の非活性状態と**連続作業時間**の起点 (直近に活性となった時点) は切り替えの完了点では確定しない。異常終了後に休息中だったのか作業中だったのか、連続作業時間を何時点から数え直すのかが未定義で、FR-15 の再起動後挙動が決まらない。

### F-05 [重大] FR-7「呼び出しから確定・離脱まで 5 打鍵以内」を縛る AD がない

能力対応表は FR-7 を AD-5 (書き込み確定点) と AD-6 (フォーカス) に割り当てるが、どちらも**入力コスト**について何も言っていない。5 打鍵は §4.1 の「数秒で完結」を検証可能にした唯一の数値であり、FR-7 の四つの結果条件のうち最も破りやすいものである。

spine には、オーバーレイ表示時にキャレットが中断メモ入力欄に入ること、確定が単一キー (Enter) で切り替えと離脱を兼ねること、タスク／ステップの選択が既定で不要であること (現在地は既知なので選択は不要) といった入力経路の固定がない。AD-3 の「Svelte → コアは Tauri command のみ」だけでは、Tab 移動・確認ボタン・タスクピッカーを挟む実装が全 AD に適合してしまう。さらに FR-7 第 3 条件 (既存メモの提示と追記選択) は打鍵数を増やす方向に働き、5 打鍵との緊張関係が解かれていない。

### F-06 [重大] FR-19「開示面はオーバーレイを閉じた時点で破棄される」が AD-2 と起動シーケンスに矛盾する

三点が互いに衝突している。

1. 起動シーケンスは 300ms 達成のためオーバーレイを起動時に生成して隠し、「以降ホットキーは表示の切替のみ」とする。隠して再表示する WebView は DOM とコンポーネント状態を保持するため、**開示状態は既定で次回呼び出しに持ち越される**。FR-19 が明示的に禁じた挙動である。
2. AD-2 は「Svelte 側は状態を保持しない」と断言する。開示面が開いているか否かは表示状態であり、AD-2 に従えばコアが持つことになる。コアが持てば、それはオーバーレイの開閉と独立に生き延びる状態となり、やはり FR-19 の「破棄される／保持されない」に反する。
3. すなわち FR-19 を満たすには「オーバーレイを閉じるコマンドが開示状態をリセットする」という明示的な規約が要るが、spine にはそれがなく、AD-2 の文言は逆にそれを書きにくくしている。

FR-19 は v1 スコープであり、かつ FR-2／賭け #1 の唯一の安全弁である。ここが曖昧なまま実装に入ると、「開いたら一覧が出たままのツール」に自然に収束する。

### F-07 [中] FR-15「休息の終了はユーザーの明示的な操作によって宣言される」の操作面がない

AD-6 は提示面を二つ (オーバーレイ／介入パネル) に固定し、AD-7 は介入への応答用ホットキーを「応答後ただちに解除する」と規定する。したがって「休息に入る」を選んだ直後、介入パネルは消え、ホットキーは解除され、休息中のツールには可視面が一つも存在しない。休息終了の宣言をどこで受けるか (オーバーレイ経由か、休息中だけ残る面か)、および「終了時に現在地は活性へ戻り FR-8 と同じ形式で提示される」という結果条件をどの面が発火させるかが未定義である。オーバーレイ経由で成立させられるため不可能ではないが、FR-15 の結果条件のうち二つが誰の責務か割り当てられていない。

### F-08 [中] FR-3「明示的な終了操作があるまで動作を継続する」の終了操作面がない

§3 は「オーバーレイは常駐プロセスの唯一の可視面」と定義し、spine はメニューバー項目・トレイ・設定画面のいずれも置いていない。明示的な終了操作をどこに置くかが未決であり、オーバーレイに置くなら FR-2 の既定表示最小化と衝突する (開示面側に置くのが自然だが、その規約もない)。軽微だが、v1 で必ず必要になる操作である。

### F-09 [中] FR-5 の分割セマンティクスは支えられている (記録のみ)

指摘ではないが検証結果として残す。「連番が再計算されても現在地は同一の作業単位を指し続ける」は、ID を UUID v7 とし「ステップ順序とは独立」と明記した一貫性規約により成立する (現在地は順序ではなく ID を指す)。分割時の前半帰属・中断メモの帰属はドメイン内の詳細であり、spine の高度で規定不要かつ阻害もない。

## 2. §7 制約 / §8 NFR の不履行・矛盾

### C-01 [重大] §8「待機時 CPU 1% 未満・メモリ 100MB 未満」が spine に一度も現れない

PRD は二重に念を押している — §8 は「当該上限は **v1 の技術選定に対する制約として働く**」、§11 は「特に**メモリ 100MB は実行基盤の選択肢を実質的に絞り込む**」。spine はスタック表で Tauri 2.11.5 / Svelte 5.57 を確定させながら、この上限に一言も触れず、測定も予算配分も行っていない。

さらに AD-6 は「この二つを同一のウィンドウ実装で兼ねてはならない」として**常時 2 つの WebView を常駐させる**構成を選んでいる。macOS の WKWebView は 1 面につき WebContent / Networking / GPU の補助プロセスを伴い、Tauri アプリの常駐フットプリントは 2 面構成では 100MB を大きく超えうる。すなわち spine は、PRD が「実行基盤の選択肢を絞り込む」と警告した数値に対し、それを悪化させる方向の決定を、数値に言及しないまま下している。

AD-8 の計時ポーリング間隔も未指定で、CPU 1% 側の根拠もない。

対応としては (a) 上限の実測と予算を spine に明記する、(b) 介入パネルを WebView ではなくネイティブ描画にして常駐面を 1 つに減らす、(c) §11 の ASSUMPTION どおり数値の見直しを PRD に差し戻す、のいずれかの決定が v1 着手前に要る。**決めないという選択肢は PRD が明示的に排除している。**

### C-02 [重大] §7.2「フルスクリーン作業中に入力先を奪ってはならない」の裏面 (そもそも見えるか) が未決

AD-6 は「入力先を奪わない」側を `canBecomeKeyWindow = false` で解いたが、FR-15 のもう一方の結果条件「いずれかが選ばれるまで介入は消えない／単純な無視によって解消されない」は、**介入がユーザーの視界に入ること**を前提とする。フルスクリーンアプリの上に NSPanel を出すには window level と collection behavior (`.fullScreenAuxiliary` 等) の指定が要るが、spine はそこを規定していない。既定のままではフルスクリーン作業中に介入が一切見えず、「無視によって解消されない」が事実上「気づかれないまま滞留する」に劣化する。PRD §7.2 が名指ししたのはまさにこの状況である。

### C-03 [中] AD-7 のグローバルホットキー一時登録は §7.2 と緊張関係にあり、その自覚がない

AD-7 は「介入の表示中のみ、二つの選択肢に対応するグローバルホットキーを登録する」とする。グローバルホットキーの登録とは、最前面アプリに届くはずのキー入力を横取りすることである。ユーザーがフルスクリーンでタイピング中に介入が出れば、その打鍵の一部がアプリに届かなくなる — §7.2 の「入力先を奪ってはならない」の文言に照らして、これは白ではない。少なくとも (a) 使用するキーの選定基準 (通常のタイピングで発生しない修飾キー組合せに限る)、(b) 登録失敗・他アプリとの衝突時のフォールバック (マウス応答のみで成立するか)、(c) 応答前に介入がクラッシュした場合の登録残存の回避、の三点が要る。(c) は AD-7 が「登録が残存したまま介入が消える経路を作ってはならない」と述べるにとどまり、異常終了経路は扱っていない。

加えて、AD-6/AD-7 は PRD §10 OQ-2 (「v1 の **UX 設計**における課題である」と明記) と addendum §3.3 が UX に委ねた決定を、アーキテクチャ側で実質的に確定させている。決定内容自体は妥当だが、所有権の越境を spine が自覚・明示していないため、UX 設計が別解 (例: 画面全体のオーバーレイ、メニューバーの点滅) を出したときに誰が勝つかが決まらない。

### C-04 [中] §8 可搬性の四境界のうち「強い提示」にアダプタの置き場がない

`ports/` の括弧書きには `storage, observation, presentation` の三つが挙がり、図にも presentation アダプタ (PR) がある。しかしソースツリーの `adapters/` 配下は `hotkey / autostart / storage / observation` の四つだけで、**`adapters/presentation/` が存在しない**。AD-6 が要求する macOS 固有コード (`NSWindowStyleMaskNonactivatingPanel`, `canBecomeKeyWindow`, tauri-nspanel の呼び出し) には行き場がなく、`commands/` か起動処理に置かれる。これは AD-1「OS API の呼び出しは `adapters/` 配下にのみ存在してよい」の即時違反であり、spine 自身の構造で spine 自身の不変条件が破れる。

関連して、「先送り」の Windows 移植項が「書き直しが必要なのは `adapters/` 配下に限られる」とするのは楽観である。addendum §3.1 は「両者に共通の抽象化レイヤは実質的に存在しない」と警告しており、AD-6/AD-7 の介入設計 (非活性パネル + 一時グローバルホットキー) は NSPanel の意味論に強く依存した**ポートの形そのもの**であって、アダプタ差し替えでは吸収できない可能性が高い。

## 3. 静かな要求 — AD 構造が黙って落としたもの (最重要)

**総論:** spine の 13 個の AD は「状態の所有・依存方向・書き込み点・フォーカス挙動・命名」を扱う。これらはすべて**構造の規律**である。PRD が最も強く主張していたのは**何を見せないか / 何を増やさないか**という**抑制の規律**であり、これに対応する AD は一つも存在しない。結果として、全 AD に忠実な builder が PRD の中心的主張をすべて破ることが可能である。以下は具体形である。

### Q-01 [重大] 設計上の三つの賭け (§1.1) が spine に一度も登場しない

AD-1..AD-13 と一貫性の規約と能力対応表を通じて、「賭け #1」「賭け #2」「賭け #3」「attention residue」「クロージャ」「grooming」のいずれの語も現れない。AD-10 は用語集の語をコード識別子に固定したが、固定されたのは**名詞**であって**主張**ではない。

PRD §1.1 と addendum §4 は、三つの賭けが一般論ではなく**ユーザー自身の放棄経験に由来する**こと、したがって「この原則を緩めることは既知の放棄要因を再導入することを意味する」ことを明記している。spine がこれを運ばないため、下流のストーリー分解と実装は、賭けを「PRD の前書きの情緒的な部分」として読み飛ばせる状態にある。

### Q-02 [重大] §5 非目標「進捗率・消化数・連続達成日数を表示しない」を守る構造がない

これを禁じる AD はゼロである。むしろ spine の構造は違反を容易にしている。

- FR-8 が要求する「第 N ステップ / 全 M ステップ」は**文字どおり進捗率の分数**である。これを数字として出すか、プログレスバーとして描くか、%表示にするかを分ける規約がない。AD-3 のイベントで N と M がフロントに渡る以上、`<progress value={n} max={m}>` は一行で書けて、どの AD にも違反しない。
- コアが持つデータ (タスク数、完了ステップ数、切り替え回数) をイベントに載せて表示することを妨げる規約もない。
- PRD は FR-16 に対してだけ「集計・進捗率・連続達成日数のいずれの形でもユーザーに表示されない」と書いたが、これは介入の決定記録 (v2) に限った文言である。v1 の表示面全体に効く禁止が spine に translate されていない。

PRD 曰く「達成の可視化は罪悪感の別形態であり、腐敗の設計思想と矛盾する」。v1 で罪悪感の装置が入れば、SM-1 (継続利用＝放棄されないこと) が直接に脅かされる。

### Q-03 [重大] 「常時の一覧表示を持たない」と賭け #3 (grooming) を守る規約がなく、FR-19 開示面が無規律のまま放置されている

spine は FR-19 開示面を `src/overlay/` に割り当て、AD-2/AD-3 で支配させる以上のことを何も言っていない。開示面に**何ができるか**の規定が皆無である。その結果、以下はすべて全 AD 適合である。

- 開示面に並べ替え・一括編集・アーカイブ・「棚卸し」ビューを足す — これは**賭け #3 が名指しした grooming そのもの**であり、PRD が「この製品の中心的な痛み」と呼んだものである。
- 開示面を閉じずに常設する、あるいは第二のウィンドウとして独立させる (F-06 の状態保持問題と合わさると自然にそうなる)。
- メニューバーやウィジェットに一覧を出す。spine は activation policy もメニューバー方針も決めていないため (F-01)、誰かがそこにタスク一覧を置いても違反する規約がない。

PRD §5 は「禁じているのは一覧の存在ではなく、求めていないときに一覧が視界に入ること」と、守るべき境界を精密に書いている。spine はこの境界を一切コードの語彙に翻訳していない。必要なのは例えば「開示面は読み取り専用の参照面であり、現在地の変更以外の変更操作を持たない」「常時可視な面はオーバーレイと介入パネルの二つのみであり、第三の可視面を作らない」といった不変条件である。

### Q-04 [重大] §9.3 の逆指標と SM-1 の判定方法に対応するデータが spine に存在しない

PRD の成功指標は四つのうち三つが観測データを要求する。spine の構造では、そのいずれも取得できない。

| 指標 | PRD の要求 | spine 下での可否 |
| --- | --- | --- |
| SM-1 継続利用 | 「週あたりのオーバーレイ呼び出し日数を目視で確認して行う」 | **不可**。呼び出しの記録を残す設計がどこにもない。ホットキーはウィンドウの表示切替だけを行う |
| SM-C1 タスク数 | 増加を目指してはならない | 可 (DB の行数を数えられる) |
| SM-C2 ツールの滞在時間 | 増加は失敗の兆候 | **不可**。オーバーレイの開閉時刻を記録する設計がない |
| SM-C3 中断メモの記入率 | 低下してはならない | **不可**。ERD は中断メモをステップに対し 0..1 で持ち、上書きされる (FR-7)。**切り替えの履歴が残らない**ため、「何回の切り替えのうち何回メモが書かれたか」が原理的に算出できない |

SM-C3 は PRD が最も強く警告した指標である — 「SM-2 は自己申告であり、『手放せるようになった』という自覚は、中断メモを書かなくなった結果として生じることがある — その場合に起きているのはクロージャではなく単なる放棄である」。つまり **v1 の唯一の中核仮説 (SM-2) が、それを打ち消す指標なしに評価される**構成になっている。

AD-12 (外部送信禁止) はこれと矛盾しない。必要なのはテレメトリではなく**ローカルの切り替えイベント履歴とオーバーレイ開閉履歴**であり、一貫性の規約の「中断メモ本文・ウィンドウタイトルなどユーザー内容はログに書かない」もメタデータの記録を禁じていない。spine は単に考慮していない。§5 非目標「進捗率・消化数を**表示**しない」は記録の禁止ではない点にも注意 (Q-02 と両立する)。

なお FR-16 (決定の記録) は v2 送りだが、それは**介入の決定**の記録であって切り替え履歴ではなく、代替にならない。

### Q-05 [中] v1 は「腐敗なしの純粋な蓄積ストア」であり、保管庫化への対抗手段が一つもない

§5 第一項「タスクの網羅的な保管庫にはならない。投入先として設計すれば、放棄されたプレーンテキスト TODO リストの再来となる」に対する PRD の唯一の構造的対抗手段は §4.7 腐敗 (FR-17/FR-18) であり、これは v2 である。PRD §6.2 はその代替を「v1 では FR-2 の既定表示最小化のみで当面代替できる」と明言している。

ところが F-03 のとおり、spine には FR-2 の最小化を構造的に守る規約がない。すなわち **PRD が指定した唯一の代替ガードが spine で無効化されている**。加えて SM-C1 の観測は可能でも (Q-04)、それを見る動機付けや閾値が下流に運ばれていない。v1 の期間は「腐敗なし・最小化保証なし」で走ることになり、これは PRD が放棄要因として特定した構成そのものである。

### Q-06 [中] addendum §4 の「原則が衝突したら出自に立ち返って優先順位を判断せよ」という規則が運ばれていない

addendum §4 は下流への明示的な指示である — 「下流で原則同士が衝突した際は、以下の出自に立ち返って判断すること」。spine は複数の緊張関係を扱いながら (AD-6 は「強い提示 vs 入力先非奪取」を解いた)、**衝突時の判断規則そのもの**を記録していない。300ms (FR-1) と耐久性 (FR-3) が衝突したとき、5 打鍵 (FR-7) と既存メモの追記選択 (FR-7 第 3 条件) が衝突したとき、賭け #1 (最小表示) と FR-8 (位置と中断メモの提示) が衝突したときに何を優先するかの根拠が、spine の内側に存在しない。

### Q-07 [軽] 非目標「汎用ランチャーにならない」に対し AD-7 が拡張の前例を作る

AD-7 は「アプリが状況に応じてグローバルホットキーを追加登録してよい」という前例を確立する。§5 はグローバルホットキーを持つことと汎用ランチャー化を明確に切り分けているが、spine 側にその切り分け (「グローバルホットキーは FR-1 の呼び出しと AD-7 の介入応答の二用途に限る」) が書かれていない。軽微だが、前例が一つあると次が通りやすいという性質の指摘である。

## 4. addendum が申し送り、spine が無視した点

### A-01 [重大] §3.1「メモリ 100MB と v2 観測実装可能性の二つを**同時に**満たす基盤を v1 着手前に検討せよ」— 片方しか実施されていない

addendum §3.1 末尾は名指しの指示である。spine は後者 (v2 で NSWorkspace による観測を `adapters/observation/` に実装できる構成) を AD-9 で満たしたが、前者 (待機時メモリ 100MB 未満) を検討した形跡が一切ない。addendum は「この二つは実行基盤の選択肢を強く絞り込む」と述べており、片方だけで基盤を確定させることを明確に禁じている。C-01 と同一の欠落だが、**PRD が「着手前に決めよ」と指定した項目を決めずに着手可能な状態にしている**点で、性質としてはより重い。

### A-02 [重大] §2.1「FR-20/FR-21 が実装されないなら観測の採用根拠が失われる」という条件が spine に一切運ばれていない

addendum §2.1 の判断表は、アクティブウィンドウ観測を「代償として OS 権限・実装量・プラットフォーム依存・プライバシー懸案が最大化する」方式として採用し、その採用根拠を FR-20 (固着の検出) と FR-21 (未宣言の切り替えの推定) が担保すると明記したうえで、**「この二つが v2 で実装されないのであれば、観測の採用根拠自体が失われる。その場合はタイマー + アイドル検出への降格を再検討すること」**と条件付きの撤退指示を出している。

spine の AD-9 と「先送り」はこの条件を運んでいない。観測ポートの存在を無条件の前提として扱い、降格の分岐を記録していない。結果として、v2 で FR-20/FR-21 が落とされても (OQ-6 の未決 — 固着への介入の提示内容が未定 — により、これは現実的なシナリオである)、アーキテクチャ側には「ならば観測をやめてアイドル検出に降格する」という再検討の引き金が残らない。§7.1 のプライバシー懸案と署名要件 (spine 自身が「先送り」で認めたコスト) を、根拠を失った機能のために払い続けることになる。

**さらに構造的な懸念:** AD-9 は観測ポートを「v1 では宣言由来の入力のみを供給する実装」で満たすと定義し、Binds に FR-15 を含めている。これはポートの形を**現在地の更新／連続作業時間の入力源** (= FR-21 の形) に寄せることを意味する。しかし FR-20 の固着検出が必要とするのは「同一の作業文脈が閾値を超えて継続していること」であり、**作業文脈の滞留時間のストリーム**である。ERD に `WORK_CONTEXT` は存在せず、§7.1 が要求する観測データの保持期限 (OQ-4) の置き場もない。AD-9 が防ぐと宣言した「v2 でドメインロジックの書き直しが必要になること」は、FR-21 については防げても FR-20 については防げていない可能性が高い。v1 でポートの型を確定させるなら、宣言由来入力と作業文脈ストリームの両方を受けられる形であることを明示すべきである。

### A-03 [中] §3.2 の耐久性要求が「トランザクション」までで止まっている

F-04 と同一。addendum §3.2 は「記憶方式の選択そのものには制約を置いていない」と自由を与えたうえで「書き込みのタイミング (切り替えの完了時点で確定していること)」を制約として渡した。spine は自由の側 (SQLite の採用) を行使し、制約の側をトランザクション境界の宣言で済ませ、「確定している」の水準 (fsync まで到達しているか) を決めていない。

### A-04 [中] §3.1 の「共通の抽象化レイヤは実質的に存在しない」という警告と、spine の移植楽観が食い違う

C-04 後段と同一。addendum は macOS と Windows に共通の抽象化が存在しないと明言しているのに対し、spine の「先送り」は「移植時に書き直しが必要なのは `adapters/` 配下に限られる」と述べる。AD-6/AD-7 が定めた介入の**ポートの形**自体が NSPanel の意味論 (非活性・キーウィンドウにならない・その上でキー応答を別経路で受ける) に依存しており、Windows ではこの形がそのまま成立しない。AD-1 の可搬性主張の範囲を、ドメインコアに限定して述べ直すべきである。

### A-05 [軽] §3.3 / OQ-2 が UX に委ねた決定を spine が確定させたことの所有権が未整理

C-03 後段と同一。決定内容は妥当であり、むしろ有用な貢献である。問題は、PRD §10 OQ-2 が明示的に「v1 の UX 設計における課題である」と帰属させた項目を spine が解いたにもかかわらず、spine 側に「OQ-2 はこの AD で解消済みとみなす／UX 設計は AD-6/AD-7 を所与として設計すること」という宣言がない点である。UX 設計が別形式を提案した場合の調停手順が存在しない。

# ARCHITECTURE-SPINE レビュー

## 0. レビューの前提

スパインは**不変条件のみを固定する文書**であり、完全な設計書ではない。したがって本レビューは「詳細が足りない」ことを指摘しない。指摘するのは次の三種のみである。

1. **その不在によって、独立に作られる二つの単位が食い違いうるもの** (= 分岐点の取りこぼし)
2. **ルールが強制不能、あるいは Prevents がルールから導けないもの** (= 拘束力のない AD)
3. **その高度が所有する構造次元が、決定も先送りも未決の問いもされずに沈黙しているもの** (= 次元の欠落)

「一人で作る趣味プロジェクトだから」という理由では減点しない。ただし**同一人物が時間をまたいで作る場合も「二人の builder」である**として扱う — 三か月後の自分は今日の暗黙の前提を持っていない。

## 1. 総評

**総合判定: adequate (重大な穴あり)。**

ドメインコアを作る基盤としては十分に強い。AD-1 / AD-4 / AD-8 / AD-10 / AD-12 / AD-13 は、いずれも**機械的に検査できる形**で書かれており、この種の文書が陥りがちな「良い心がけの列挙」になっていない。特に AD-4 の「フロントエンドのコードに SQL 文字列が存在してはならない」と AD-8 の「フロントエンドは経過時間を数えない」は、grep 一回で違反が検出できる。PRD からの導出も誠実で、パラダイム選択を「本スパインの発明ではなく、PRD §8 可搬性が既に規定したものを批准したもの」と明示している点は、下流が原則を再議論することを正しく防いでいる。

一方で、**プロセス境界と UI 境界の側は build substrate として未完成である。** 核心の不変条件である AD-2 が、文書内の他の規定 (AD-5, FR-19) によって字義どおりには成立しない形で書かれており、この一点だけで AD-2 の拘束力は実質的に失われている (C3)。また AD-2 + AD-3 は Tauri 上での状態分岐を**防ぎきれていない** — イベント欠落に対する再同期の規定がなく、しかも本スパインが選んだ「起動時にウィンドウを生成して隠す」構成はイベント欠落が最も起きやすい構成である (C2)。加えて、memlog が「必須」と明記した NSPanel の二つの設定がスパインへの蒸留時に落ちており、これが欠けると FR-15 は PRD §7.2 が名指しした状況でのみ動かない — 最も気づきにくい壊れ方をする (C1)。

運用・環境の次元 (dev 実行と実配置の共存、DB ファイルの所在、スキーマ移行、ログの所在) はほぼ全面的に沈黙している。AD-13 が扱っているのは配布経路の一点のみで、次元全体を覆っていない。

**v1 の実装に着手してよい。ただし C1〜C3 と H5 は最初のストーリーを切る前に閉じること** — いずれも後から足すと既に書いたコードの書き直しになる種類の穴である。

## 4. Critical

### C1 — AD-6 が memlog の「必須」条件を二つ落としており、FR-15 が PRD §7.2 の状況でのみ機能しない

**対象:** AD-6 / スタック表の `tauri-nspanel`
**該当箇所 (AD-6 Rule):**

> 介入は非活性パネル (`NSWindowStyleMaskNonactivatingPanel`, `canBecomeKeyWindow = false`) として実装し、いかなる場合もキーボードの入力先を奪わない。

**問題:** memlog は同じ論点について、二つの追加条件を**必須**と明記している。

> (constraint) 介入パネルには set_hides_on_deactivate(false) と full_screen_auxiliary の collection behavior が必須。**後者がないとフルスクリーン作業中に介入が表示されず、PRD §7.2 が名指しした状況で機能しない**

この二つがスパインに引き継がれていない。`full_screen_auxiliary` (NSWindowCollectionBehaviorFullScreenAuxiliary) が欠けた NSPanel は、他アプリのフルスクリーン Space 上に出ない — macOS がパネルを別 Space に置いたままにするため、パネルは「表示されている」が**ユーザーには見えない**。`set_hides_on_deactivate(false)` が欠ければ、アプリが非アクティブになった瞬間 (= 介入が出る状況そのもの) にパネルが自動的に隠れる。

**なぜ Critical か:** 壊れ方が静かである。開発中はアプリがフォアグラウンドかつ非フルスクリーンなので、パネルは正常に出る。壊れるのは PRD §7.2 が名指しした状況「**特にフルスクリーンでの作業中および入力中に**」だけであり、それは FR-15 が最も必要とされる状況である。しかも AD-6 の Prevents は「あるいは逆にオーバーレイがフォーカスを取れず中断メモを入力できないこと」までしか想定しておらず、「パネルが出ない」という失敗様式を視野に入れていない。

**最小の修正:** AD-6 の Rule に一文追加する。「パネルには `set_hides_on_deactivate(false)` と `NSWindowCollectionBehaviorFullScreenAuxiliary` を設定する。後者を欠く実装は PRD §7.2 の状況で介入が不可視となるため、受け入れ不可とする。」検証条件も併記できる — 「他アプリのフルスクリーン中に介入が視認できること」は手で確かめられる。

### C2 — AD-2 + AD-3 は Tauri 上の状態分岐を防ぎきれない。再同期の規定がない

**対象:** AD-2, AD-3 (問われた論点への回答を兼ねる)
**該当箇所 (AD-2 Rule):**

> Svelte 側は状態を保持しない。画面に出す値はすべてコアから受け取った直後の写しであり、ユーザー操作はコアへのコマンドとしてのみ表現される。

**該当箇所 (AD-3 Rule):**

> Svelte → コアは Tauri command のみ (戻り値は結果であって状態の所有権ではない)。コア → Svelte は Tauri event のみ。

**問題:** この二つは**必要だが十分ではない**。所有権の所在 (AD-2) と書き込み方向の一方向性 (AD-3) を固定しても、**写しが古くなる経路**は塞がれていない。Tauri の event は fire-and-forget であり、リプレイも配送保証もない。listener が登録される前に emit されたイベントは、単に失われる。

そして本スパインが選んだ構成は、その欠落が最も起きやすい構成である。「起動と常駐」の図はこう規定している。

> Core->>Ov: ウィンドウを生成し隠す
> Core->>Panel: パネルを生成し隠す
> Note over Core,Ov: 以降ホットキーは表示の切替のみ<br/>生成しないため 300ms を満たす (FR-1)

つまり**二つの webview が、大半の時間、隠れた状態で生きている**。この間もコアは計時し (AD-8)、介入を発し (FR-15)、現在地を動かしうる。隠れている webview が listener を張っていれば受け取れるが、webview のリロード、OS のリソース回収、初期化順序 (ウィンドウ生成直後・スクリプト評価前に発火した event) のいずれでも欠落は起きる。欠落すると、オーバーレイは**次にホットキーで呼ばれたとき、古い現在地を表示する**。AD-2 の Prevents 「現在地が二重化して FR-6 の一意性が壊れること」は、コア内部では確かに防がれている (「現在地を変更しうるコードパスはコア内に一つだけ存在する」は強い) が、**画面に見えている現在地とコアの現在地が食い違う**という形の二重化は防がれていない。ユーザーから見れば後者も同じ症状である。

さらに悪いことに、この故障は再入コストを直撃する。FR-8 が返す「第 N ステップ / 全 M ステップ」と中断メモが古ければ、それはこのツールが防ごうとしているもの (誤った文脈での再開) をツール自身が作り出すことになる。

**足りない三本目の脚:** 「**表示面は、可視化される時点でコアから完全なスナップショットを引き直す。event は差分更新の最適化であって、真実の唯一の供給路ではない**」という規定。これがあれば event 欠落は自己修復する。ホットキーで呼ばれるたびに 1 回 command を投げるだけであり、300ms 予算にも収まる (SQLite の 1 クエリ)。

**最小の修正:** AD-2 または AD-3 に追加する。「ウィンドウが不可視から可視へ遷移するとき、表示に必要な状態はコマンドで取得し直す。event の取りこぼしが画面に残留してはならない。」

### C3 — AD-2 の Rule は文書内の他の規定によって字義どおりには成立しておらず、その結果として拘束力を失う

**対象:** AD-2 (vs AD-5, FR-19)
**該当箇所:**

> **Rule:** Svelte 側は状態を保持しない。

**問題:** このルールは、同じスパインの中の二か所と矛盾する。

1. **AD-5:** 「入力途中のメモは永続化しない」。永続化しないのなら、確定前の中断メモ本文は**どこかに存在しなければならない** — そしてその場所は textarea、すなわち Svelte 側である。AD-5 は「入力途中の状態はフロント側にしか存在しない」ことを暗黙に要求しながら、AD-2 はそれを禁じている。
2. **FR-19 (v1 スコープ):** 「開示面は**オーバーレイ**を閉じた時点で破棄され、次回の呼び出し時に初期表示 (FR-2) へ戻る。開示状態は保持されない。」 — 「開示面を開いているか否か」は状態である。これをコアに置けば、UI の都合がドメインに染み出す (AD-1 の精神に反する)。フロントに置けば AD-2 の字義に反する。

**なぜ Critical か:** 問題は「例外が二つある」ことではなく、**builder が最初のストーリーで AD-2 を破らざるをえない**ことにある。一度破られた不変条件は、以後の判断基準として機能しない — 「textarea のために既に破っているのだから、タスク一覧をフロントにキャッシュするのも同じ程度の逸脱だろう」という推論を止めるものが何もなくなる。不変条件は、守れる形で書かれていなければ不変条件ではない。

スパインが本当に固定したいのは「**ドメイン状態**の所有者はコアである」であって「フロントに変数を置くな」ではない。その区別が言語化されていない。

**最小の修正:** AD-2 の Rule を二層に書き分ける。

- フロントが保持してよいもの: 確定前の入力内容、開示面の開閉、スクロール位置、アニメーション状態 — いずれも**オーバーレイを閉じた時点で破棄されるもの**に限る (この条件は FR-19 の要求とそのまま一致する)。
- フロントが保持してはならないもの: 現在地、タスク、ステップ、中断メモの確定値、連続作業時間 — すなわちコアが真実を持つ値。これらは受け取った直後の写しとしてのみ画面に出る。

「オーバーレイを閉じたら消えるか」という判定条件を与えれば、このルールは builder が自分で判定でき、かつ機械的にも検査しやすくなる。

## 5. High

### H1 — AD-9 の観測ポートは、v1 のコードが書き直しにならない程度には特定されていない

**対象:** AD-9 (問われた論点への回答を兼ねる)
**該当箇所:**

> ### AD-9 — 観測ポートは v1 で定義し、**実装を持たない**
> **Rule:** v1 の時点でコアに観測ポート (トレイト) を定義する。v1 では宣言由来の入力のみを供給する実装を置き、v2 でアクティブウィンドウ観測の実装に差し替える。コアは入力の出所を区別しない。

**問題は三つある。**

**(a) 見出しと Rule が矛盾している。** 見出しは「実装を持たない」、Rule は「実装を置く」。v1 は実装を持つ (宣言由来のもの) のだから、見出しが誤りである。スパインは短いがゆえに見出しだけが記憶される文書であり、この不整合は「v1 では何も書かなくてよい」という読みを許す。

**(b) ポートの形が一切決まっていない。** 「トレイトを定義する」としか書かれておらず、下記のいずれも未定である。

- **押すか引くか** — コアが定期的に `current_context()` を呼ぶのか、アダプタが変化時にコアへ通知するのか。これは v1 のコアのループ構造そのものを決める。
- **何を運ぶか** — PRD §3 は**作業文脈**を「最前面のアプリケーション名とウィンドウタイトルの組」と定義し、同時に「**同一とみなす粒度は v1 の対象外である**」と明記している。粒度が未定義ということは、v1 のポートは「同一性を判定できない値」を運ぶことになる。しかし FR-20 (固着) は「作業文脈が閾値を超えて変化せず」を判定条件とする — すなわち**同一性判定こそが v2 の中核**である。この判定がコア側にあるのかアダプタ側にあるのかが未定のままポートを切ると、v2 で必ず境界を引き直す。
- **無効状態をどう表現するか** — FR-11 は「OS 権限が未付与の場合、ツールは本機能を無効化した状態で他機能を継続動作させ、**その旨をユーザーに示す**」を要求する。したがってポートは「観測不能」という状態を返せなければならず、かつそれが UI まで届かなければならない。この状態が v1 のトレイトに無ければ、v2 でシグネチャが変わる — **AD-9 が防ぐと宣言したまさにその書き直し**が起きる。
- **保持期間** — §7.1 は観測データに保持期限を課す (OQ-4 で期間のみ未決)。保存を伴うのなら、ポートとストレージの関係が v1 の時点で決まっている必要がある。

**(c) 「コアは入力の出所を区別しない」が、v1 の供給元では成立しない。** 宣言由来の入力 (ユーザーが切り替えを宣言した) は**作業文脈を含まない** — アプリ名もウィンドウタイトルも存在しない。したがって v1 の実装は、存在しない値を合成するか、ポートを「作業文脈を運ばない何か」として定義するかのどちらかになる。前者は無意味な値をコアに流し込み、後者は v2 で型が変わる。

**AD-9 が本当に固定すべきだったこと:** ポートの存在ではなく、**コアの状態機械が何によって駆動されるか**である。すなわち「連続作業時間・固着・切り替え推定は、いずれも**同一形式の入力イベント列**を消費する。v1 ではその列をユーザーの宣言が生成し、v2 では観測が生成する。コアは列の生成元を知らない」と書けば、v1 のコードは v2 でそのまま使える。現在の書きぶりは「トレイトを置け」までしか言っておらず、**書き直しを防ぐのはトレイトの存在ではなくコアの駆動形式である**という要点を落としている。

**判定: thin。** 意図は正しく、置き場所 (`ports/observation`) も正しいが、v1 のコードが v2 で無傷で残る保証にはなっていない。

### H2 — スタック表の `rusqlite または sqlx` は未決定であり、コア全体の同期/非同期を決めてしまう

**対象:** スタック表 / AD-4
**該当箇所:**

> | SQLite | rusqlite または sqlx 経由 (`tauri-plugin-sql` は不使用 / AD-4) |

**問題:** これはスパイン内で唯一「または」が残っている技術選択であり、しかも最も影響範囲が広い。sqlx は非同期前提であり、採用すれば storage ポートのトレイトは `async_trait` になり、それを呼ぶドメイン関数も非同期に染まり、計時ループも tokio に乗る。rusqlite は同期であり、コアは素の関数のままでよく、ブロッキング呼び出しを Tauri の非同期境界でどう扱うかという別の問題が出る。マイグレーション機構も異なる (sqlx はコンパイル時検査とマイグレーションを内蔵、rusqlite は `rusqlite_migration` 等の別依存)。

**なぜ High か:** 二人の builder が別々のストーリーを取れば、片方は `async fn save_switch`、片方は `fn save_switch` を書く。これは後から片方を直せば済む話ではなく、**コアの全関数シグネチャ**が変わる。スパインが所有すべき典型的な分岐点であり、「または」のまま残してよい種類の選択ではない。

**最小の修正:** どちらかに決めるか、「コアは同期とし、非同期境界はアダプタ層に閉じる」という**性質の方**を固定する (そうすれば rusqlite が導かれる)。本件の規模とクエリ形状からは rusqlite + 同期コアが素直であり、計時は専用スレッドで持てる。

### H3 — AD-5 は SQLite の耐久性設定を固定していないため、PRD §8 の約束を保証できない

**対象:** AD-5
**該当箇所:**

> **Rule:** 現在地の移動と中断メモの確定は単一のトランザクションで書き込む。入力途中のメモは永続化しない。**プロセスが異常終了した場合、最後に完了した切り替えの状態に復帰する。**

**問題:** 前二文は強制可能だが、第三文は**結果**であって規則ではなく、しかも耐久性設定に依存する。PRD §8 の要求はより強い。

> **データ堅牢性** — **現在地**および**中断メモ**は、**プロセスの異常終了および OS の強制終了**をまたいで失われない (FR-3)。

WAL モード + `synchronous = NORMAL` (sqlx / 多くのラッパのデファクト設定) では、**プロセスのクラッシュには耐えるが OS/電源断では直近のトランザクションを失いうる**。すなわち AD-5 の Rule をそのまま実装しても、PRD が明示的に挙げた「OS の強制終了」条件は満たされないことがある。しかも H2 が未決なので、どちらのライブラリを選ぶかでデフォルトが変わる。

**なぜ High か:** Prevents 「確定済みの切り替えが失われること」がルールから導けていない。かつ、この故障は**失われて初めて分かる**種類のものであり、テストされない限り永久に気づかれない。

**最小の修正:** AD-5 に一文。「SQLite は WAL モード、`synchronous = FULL` とする。切り替えの確定は 1 トランザクション 1 fsync で完了させる。」1 日数十回の書き込みしかないため、FULL の性能コストは本件では無視できる。

### H4 — AD-7 に登録失敗時の経路がなく、Prevents が導けない。ホットキーの同定もない

**対象:** AD-7
**該当箇所:**

> **Prevents:** 非活性パネルがキーボードを受け取れないために、介入の二択がマウス操作を強制すること
> **Rule:** 介入の表示中のみ、二つの選択肢に対応するグローバルホットキーを登録する。応答後ただちに解除する。登録が残存したまま介入が消える経路を作ってはならない。

**問題が三つ。**

1. **登録は失敗しうる。** グローバルホットキーは OS 全体で一意であり、他アプリが既に押さえていれば登録は失敗する。失敗時の規定がないため、Prevents は成立しない — その場合ユーザーはマウスを強制される。さらに悪いのは FR-15 との組み合わせで、「いずれかが選ばれるまで**介入**は消えず、単純な無視によって解消されない」。**登録に失敗した非活性パネルは、キーボードで閉じられず、消えもしない。** 非活性 NSPanel はクリック自体は受け取れるのでマウスでは操作できるが、それは AD-7 が防ぐと宣言した状態そのものである。
2. **どのキーかが決まっていない。** 「二つの選択肢に対応するグローバルホットキー」としか書かれていない。FR-1 のホットキーと衝突してはならず、かつ介入中に押しやすい必要がある。ストーリーごとに別のキーが選ばれうる。
3. **FR-1 のホットキーとの関係が未定。** 介入表示中に FR-1 のホットキーが押されたら何が起きるか (オーバーレイが前に出る / パネルが背面に回る / 両方出る) が規定されていない。オーバーレイは通常ウィンドウとしてフォーカスを取る (AD-6) ので、この組み合わせは実際に起こる。

**最小の修正:** AD-7 に「登録に失敗した場合はパネル上のクリック可能な二択に縮退し、その旨をパネル上に示す。介入が閉じられない状態を作ってはならない」を追加。ホットキーの実体は規約表か AD-7 に固定する。解除漏れは RAII (パネルの生存に束ねた登録ガード) にすれば「経路を作ってはならない」という禁止形が型で担保される。

### H5 — 提示面が「二種類」では足りない。FR-3 の明示的終了、FR-15 の閾値変更、FR-1 のフォーカス復帰に居場所がない

**対象:** AD-6 / FR-1 / FR-3 / FR-15
**該当箇所:**

> ### AD-6 — 提示面は二種類あり、フォーカス挙動が異なる

**問題:** v1 スコープの要求のうち、次の四つが architecture 上のどこにも割り当てられていない。

1. **FR-3 の明示的終了** — 「明示的な終了操作があるまで動作を継続する」。終了操作が存在することが前提だが、Dock アイコンもメニューバー項目も規定されていないため、**終了する手段が設計上存在しない**。
2. **FR-15 の閾値変更 (v1 スコープ)** — 「閾値の既定値は 50 分とし、**ユーザーが変更できる**」。AD-11 は設定の**保存場所**を固定したが、**編集面**を誰も持っていない。オーバーレイの開示面に載せるのか、別ウィンドウなのか、v1 は DB を直接いじるのかで builder は分岐する。
3. **activation policy** — 常駐アプリが Dock アイコンを持つか (`NSApplicationActivationPolicyRegular`) 持たないか (`.accessory` / `LSUIElement`) は構造的決定である。Regular のままだとログイン時起動 (FR-3) で Dock に現れ、起動時にフォーカスを奪いうる。この選択は FR-1 のフォーカス復帰挙動にも直結する。
4. **FR-1 のフォーカス復帰** — 「呼び出し前に最前面であったアプリケーションは、**オーバーレイ**を閉じた時点でフォーカスを回復する」。通常ウィンドウとしてフォーカスを取った (AD-6) 以上、閉じたときの復帰は macOS 固有の明示的処理を要する (`NSApp.hide` 等) — つまり**アダプタ層の責務**だが、`adapters/` の一覧にも「能力 → アーキテクチャ対応」表にも現れない。表では FR-1 は「`adapters/hotkey/` + 事前生成済みウィンドウ」とされており、フォーカス復帰の責務者がいない。

**なぜ High か:** 1 と 2 は v1 の検証可能な結果条件であり、「無い」ままリリースすると FR-3 と FR-15 が未達になる。3 は後から変えると起動・フォーカス周りの挙動が全部ずれる。4 は FR-1 の三条件のうち一つが実装されない形で見過ごされやすい。

**最小の修正:** AD-6 を「提示面は三種類」に拡張する (オーバーレイ / 介入パネル / メニューバー項目) か、少なくとも「常駐の可視点と終了・設定の到達経路」を一つの AD か未決の問いとして立てる。activation policy はスタック表か AD-6 に一行で固定できる。

### H6 — 運用・環境の次元がほぼ全面的に沈黙している

**対象:** 文書全体 (AD-13 が唯一の接点)
**該当箇所 (AD-13 Rule):**

> ビルドから `/Applications` への配置までを単一の make タスクに集約する。署名は v1 では行わない。

**問題:** AD-13 は配布経路の一点だけを扱っており、運用・環境という次元全体を覆っていない。次のいずれも、決定も先送りも未決の問いもされていない。

- **SQLite ファイルの所在** — `~/Library/Application Support/<bundle-id>/` なのか、リポジトリ内なのか。このツールの価値は蓄積されたデータそのものであり、所在が未定のまま複数のストーリーが DB を開く。
- **開発実行と実配置の共存** — AD-13 は `/Applications` に常駐アプリを置く。その状態で `tauri dev` を走らせると、**同じグローバルホットキーを二つのプロセスが取り合い** (後発の登録は失敗する = H4 の失敗経路が日常的に発生)、**同じ DB ファイルを二つのプロセスが開く**可能性がある。これは AD-2 の「状態の唯一の所有者」がプロセス境界で崩れる唯一の現実的経路である。macOS では同一 .app の二重起動は LaunchServices が抑止するが、**dev ビルドは別バイナリなので抑止されない**。dev と本番で bundle id / DB パス / ホットキーを分けるか否かは、着手前に決めるべき環境の決定である。
- **スキーマ移行** — 個人ツールは年単位で同じ DB を使い続ける。テーブル追加のたびに二人の builder が別の方法 (手書き ALTER / 再作成 / マイグレーション表) を採れば、データは失われる。
- **バックアップ/復旧** — §7.1 によりクラウド同期は無い。端末が壊れたら全部消える構成であり、それが受容された判断なのか見落としなのかが読めない。
- **ログの所在・回転・保持** — 規約は「ローカルファイルへの追記のみ」と内容制限 (ユーザー内容を書かない) は決めたが、**どこに、いつまで**が無い。終日常駐するプロセスの追記専用ログは、規定が無ければ無限に伸びる。

**なぜ High か:** この次元の沈黙は「まだ決めていない」ではなく「所有していることに気づいていない」に見える。特に dev/本番の共存は、最初の一週間で必ず踏み、しかも症状 (ホットキーが効かない・データが古い) から原因に辿り着きにくい。

**最小の修正:** 「運用の envelope」として 5 行程度の節を足すか、決めないものは先送りに明記する。決定が要るのは実質二点 — DB の所在と、dev/本番を分けるか否か。

## 6. Medium

### M1 — `tauri-nspanel` はバージョンを持たず、単独保守の git ブランチ依存である

スタック表で唯一バージョン欄が空白になっている。

> | tauri-nspanel | 非活性パネル用 (AD-6) |

2026-09 時点でも tauri-nspanel は crates.io の安定版ではなく、Tauri 2 系では `branch = "v2.1"` のような **git ブランチ指定**で使うのが通常である。すなわち (a) 再現可能なビルド (AD-13 の make タスク) のためには**コミットハッシュの固定**が要る、(b) 単独保守であり Tauri のマイナー更新に追随しない期間が生じうる、(c) それでいて AD-6 という load-bearing な不変条件を単独で支えている。Tauri 本体側にも NSPanel 型ウィンドウの要望 issue があり、将来本体に吸収される可能性がある。

**最小の修正:** 固定するコミット/ブランチをスタック表に書く。加えて「このプラグインが Tauri の更新に追随しなくなった場合、`objc2` 経由で直接 NSPanel を構成する経路に落ちる」という退避先を一行で記す (AD-6 の Rule は API 名で書かれているので、実現手段が変わっても不変条件は生き残る — その点は良い設計である)。

### M2 — イベントのペイロード契約 (スナップショットか差分か) が未定

規約は event の**命名** (`名詞_過去分詞`) を固定したが、**何を載せるか**を固定していない。AD-2 が「画面に出す値はすべてコアから受け取った直後の写し」と規定した以上、フロントは event だけで描画できる必要がある — が、`current_position_changed` が空の通知なのか完全な状態なのかで、フロントの構造は全く別物になる。二人の builder が別の event を追加すれば、片方は通知+再取得、片方は自己完結ペイロードになる。C2 の再同期規定と合わせて一度に決められる。

### M3 — ステップ順序の表現が未定で、FR-5 の連番再計算と噛み合わない

FR-5 は「**ステップ**の追加により後続の**ステップ**の連番が再計算されても、**現在地**は同一の作業単位を指し続ける」を要求する。スパインは UUID v7 に「生成順に単調増加し、**ステップ順序とは独立**」と注記しており、これは「id で並べるな」という良い先回りである。しかし順序を持つ実体 (連番カラムを毎回振り直すのか、疎な整数/分数のソートキーを持つのか) は未定。FR-5 の分割 (「**現在地**は分割後の前半を指す」「**中断メモ**は分割後の前半に帰属する」) を実装するストーリーが二つに分かれれば、表現が食い違う。ERD の `TASK ||--|{ STEP : "1..N を順序付きで内包"` は関係は示すが表現を決めていない。

### M4 — AD-10 の対応表に、現在地の**活性/非活性**の識別子がない

AD-10 は「用語集の語と識別子は 1:1」を宣言し、19 語を固定している。しかし PRD §3 の現在地の定義は「**活性**と**非活性**の二状態を持ち」を含み、FR-15 の結果条件も「**現在地**は値を保持したまま**非活性**となり」と書く。この二語だけが表にない。結果、`is_active: bool` / `PositionState::{Active, Inactive}` / `Resting` のいずれかに分岐する。AD-10 の Prevents が挙げた「`currentPosition` / `pointer` / `cursor` のように複数の名前で実装され」という故障が、まさにこの語で起きる。同様に**閾値**も v1 の設定値として現れるが表にない。

### M5 — AD-8 が所有する「計時」の時計種別とスリープ跨ぎの挙動が未定

AD-8 は計時の**所有者**を正しく固定したが、**何で測るか**を決めていない。Rust の `Instant` (単調) と `SystemTime` (壁時計) では、macOS のスリープ・蓋閉じを跨いだときの経過量が変わりうる。連続作業時間 50 分閾値のツールで、3 時間の蓋閉じが「3 時間の作業継続」と数えられれば、復帰直後に休息介入が暴発する。PRD §6.3 は「宣言せずに離席した場合」の誤発火を v1 で許容しているが、それは**宣言の欠落**に由来する誤りの許容であって、時計種別の選択ミスまで許容したものではない。規約の「時刻は UTC の ISO 8601 で保持し」「期間は秒の整数」は**保存形式**を決めただけで、計測の時計を決めていない。

### M6 — 腐敗 (FR-17) の先送りが、v1 側のデータ取得義務を落としている

先送りにはこうある。

> - **腐敗 (FR-17, FR-18) の判定と復帰** — v2。判定期間の初期値は PRD OQ-3 として未決。

判定ロジックを v2 に送るのは正しい。しかし FR-17 の判定は「**一定期間現在地とならなかったタスク**」であり、これは**タスクが最後に現在地となった時刻**という履歴を必要とする。v1 がこの値を記録しなければ、v2 で腐敗を実装した時点では過去の履歴が存在せず、判定は v2 導入時点からしか数えられない — つまり v1 を長く使うほど、腐敗機能が効き始めるのが遅れる。

加えて FR-19 は **v1 スコープ**でありながら、結果条件に「開示面は**腐敗**した**タスク**を含まない (FR-18 の経路と区別される)」を含む。v1 に腐敗が無ければこの条件は自明に満たされるが、v2 で腐敗を足す際に FR-19 のクエリ側を変更する必要がある、という事実は記録されていない。

**最小の修正:** 先送りの当該項目に一行。「ただし v1 の時点で、タスクが最後に現在地となった時刻を記録する。判定ロジックのみを v2 に送る。」

### M7 — Tauri v2 の capability/permission と webview の CSP が沈黙している

Tauri 2 は、どのウィンドウがどのコマンドを呼べるかを capability ファイルで宣言する仕組みを持つ。本件は**二種類のウィンドウ**を持ち、しかも介入パネルはオーバーレイと権限が同じである必要がない。この設定は単なる実装詳細ではなく、**AD-2 / AD-4 / AD-12 を規律から機械的強制に格上げできる唯一の場所**である (例: 介入パネルから状態変更コマンドを呼べなくする、webview から外部オリジンへの接続を CSP で禁じて AD-12 をコードレビュー依存でなくする)。次元として沈黙しているのは惜しい。

### M8 — 並行実行モデル (計時ループの実行主体) が未定

AD-8 はコアが計時を所有すると定めたが、それが専用スレッドなのか tokio のタスクなのか、コアの状態が `Mutex` の後ろにあるのか単一スレッドに閉じているのかは未定。H2 (rusqlite か sqlx か) と連動しており、二つ合わせて Rust 側のコードの形を決めてしまう。イベント発行 (規約「変更後は必ず event を発行する」) がロック保持中に起きるか否かも、この決定に従属する。

### M9 — AD-3 の「配って回る」条項は測定不能で、字義どおりなら通常の component 合成まで禁じる

> Svelte が別の Svelte モジュールへ状態を配って回ることを禁じる。

意図は「フロント側に真実の源になる store を作るな」であろうと読めるが、字義どおりには**親から子への props** も「別のモジュールへ状態を配る」に該当してしまう。何が違反かを builder が判定できない条項は、判断基準として機能しない。C3 の修正 (ドメイン状態 vs 一時的表示状態) を入れれば、この条項は「**ドメイン状態**をフロント側の共有ストアに保持しない」と書き直せて測定可能になる。

### M10 — AD-8 に時計のポートがなく、先送りが根拠とした「単体テストは容易」が成立しない

先送りにはこうある。

> - **テスト戦略** — 未決。**ドメインコアが OS 非依存である (AD-1) ため単体テストは容易だが**、v1 の規模では方針を固定する必要がない。

先送り自体は妥当である。しかし根拠が正しくない。コアが所有する最も検証困難なロジックは計時 (連続作業時間・猶予・腐敗判定) であり、`ports/` の列挙は「(storage, observation, presentation)」の三つで、**時計がポートになっていない**。時計がコア内部で直接取得されるなら、50 分閾値のテストは 50 分待つことになる。OS 非依存であることは、時間依存ロジックがテスト可能であることを意味しない。

**最小の修正:** `ports/` に clock を加える (一行)。これは AD-9 の観測ポートと同型の話であり、同じ理由で v1 のうちに切っておく価値がある。

## 7. Low

### L1 — AD-1 はモジュール境界であり、コンパイラに強制させられていない

`domain/` と `adapters/` が同一クレート内のモジュールである限り、`use tauri::...` を domain に書いてもビルドは通る。AD-1 の Rule 自体は明確で grep 可能なので実務上は十分だが、`domain` を依存を持たない別クレートに切れば、規律ではなく**コンパイルエラー**として強制される。スパインの規模では任意だが、「可能性のみ維持する」(Windows 移植) という先送りの主張を実際に保証する最も安価な手段でもある。

### L2 — Gatekeeper の初回起動手順が memlog からスパインへ引き継がれていない

memlog:

> (decision) 配布はローカルビルドの .app を /Applications に置く。署名なし。**Gatekeeper は初回の右クリック起動で回避する**

AD-13 は「署名は v1 では行わない」までしか書いておらず、回避手順が落ちている。C1 ほど致命的ではないが、AD-13 の Prevents が「ビルド手順の面倒さが修正の動機を殺すこと」である以上、初回に必ず出る Gatekeeper の壁は Prevents の対象そのものである。make タスクの手順に一行入れれば済む (`xattr -dr com.apple.quarantine` を配置時に実行する等)。

### L3 — Vite と Rust ツールチェインのバージョンが固定されていない

> | Vite | Svelte テンプレート同梱の最新 |
> | Rust | stable (edition 2021 以降) |

他の行が具体的なバージョンを持つ中で、この二つだけが浮動している。AD-13 が「単一の make タスク」で再現性を主張する以上、`rust-toolchain.toml` と lockfile の扱いは一行で決められる。なお `tauri-plugin-global-shortcut` は Rust 1.77.2+ を要求するため、下限は実質的に存在する。

### L4 — `edition 2021 以降` は 2026 年時点では古い書き方

edition 2024 は 2025-02 の Rust 1.85 で安定化しており、新規プロジェクトの既定である。「2021 以降」は誤りではないが、新規に切るプロジェクトの記述としては情報がない。`edition 2024` と書けば済む。

## 8. 特に問われた三点への回答

### (a) AD-2 と AD-3 は、Tauri アプリの状態分岐を実際に防ぐのに足りているか

**足りていない。** 二つのうち片方 (コア内部の一意性) は確かに防がれているが、もう片方 (画面とコアの乖離) は防がれていない。

防がれている側は強い。AD-2 の「**現在地を変更しうるコードパスはコア内に一つだけ存在する**」は、この文書で最も価値の高い一文である。これがあれば FR-6 の一意性は構造的に保証され、FR-5 の連番再計算や FR-15 の休息遷移が現在地を触っても、経路が一つである限り不整合は作れない。

防がれていない側が C2 と C3 である。**AD-2 は所有権を、AD-3 は方向を固定したが、どちらも「写しの鮮度」を扱っていない。** Tauri の event は配送保証がなく、本スパインは「起動時に二つのウィンドウを生成して隠す」構成を選んだため、隠れている webview が event を取りこぼす経路が常時開いている。さらに C3 により、AD-2 は最初のストーリーで破られることが確定しているため、拘束力そのものが弱い。

三本目の脚として必要なのは、**可視化時のスナップショット再取得**という一行 (C2)、および**ドメイン状態と一時的表示状態の線引き** (C3) である。プロセス境界 (dev と本番の二重起動) の穴 (H6) も、同じ「所有者は一つ」という主張が別の次元で破れる経路である。

### (b) AD-6 と AD-7 は、FR-15 と §7.2 を**同時に**満たしているか

**設計としては満たしている。実装条件としては満たしていない。**

方針は正しい。二つの緊張 (「選ばれるまで消えない」と「入力先を奪わない」) を、**ウィンドウ種別を二つに分ける**ことで解いたのは的確な解であり、PRD が UX 設計に委ねた OQ-2 に対する妥当な技術解である。「この二つを同一のウィンドウ実装で兼ねてはならない」という禁止形も、後から「一つで済むのでは」と再統合されることを正しく防いでいる。AD-7 の一時登録ホットキーも、非活性パネルがキーボードを取れないという制約を迂回する筋の通った手である。

同時に満たせていないのは次の二点。

1. **C1** — memlog が「必須」とした二設定が落ちている。`full_screen_auxiliary` が無ければ、パネルは PRD §7.2 が名指しした「フルスクリーンでの作業中」にだけ出ない。すなわち FR-15 が最も要る場面でのみ機能しない。これは §7.2 を満たさないのではなく、**FR-15 を満たさない**という失敗である。
2. **H4** — ホットキー登録が失敗した場合の規定がない。FR-15 の「いずれかが選ばれるまで消えない」と組み合わさると、**閉じる手段のない介入**という最悪の状態が構成可能になる。これは §7.2 の「不可逆な結果を招いてはならない」の精神に反する。

この二つを閉じれば、AD-6 + AD-7 は FR-15 と §7.2 を同時に満たす。

### (c) AD-9 は、v1 のコードが書き直しにならない程度に特定されているか

**されていない (H1)。** 見出しと Rule が矛盾し、ポートの形 (押す/引く、何を運ぶ、無効状態、保持) が一切未定で、かつ「コアは入力の出所を区別しない」という要となる主張が、作業文脈を持たない v1 の供給元では成立しない。

AD-9 が固定すべきだったのはトレイトの**存在**ではなく、**コアの状態機械が消費する入力の形式**である。「連続作業時間・固着・未宣言の切り替えは、いずれも同一形式の入力列を消費する。v1 ではユーザーの宣言がその列を生成し、v2 では観測が生成する」と書けていれば、v1 のコアは v2 でそのまま残る。現状の書きぶりでは、v2 で作業文脈の同一性判定と権限未付与状態を導入する時点で、トレイトのシグネチャと呼び出し側の両方が変わる可能性が高い。

## 10. 評価すべき点 (過剰修正を避けるために)

指摘の量から逆の印象を持たないために、機能している部分を明記する。

- **AD-2 の「現在地を変更しうるコードパスはコア内に一つだけ存在する」** — 文書中で最も価値の高い一文。FR-6 を構造的に保証している。
- **AD-4 の「フロントエンドのコードに SQL 文字列が存在してはならない」** — 検査可能な形で書かれた禁止であり、`tauri-plugin-sql` を名指しで排除した根拠 (memlog: 「同プラグインはフロントから SQL を発行する設計であり『状態の所有者は Rust コア』の不変条件と衝突する」) も明快。
- **AD-8 の「フロントエンドは経過時間を数えない」** — 「表示上の秒数も、コアから受け取った値の描画であって独自の計時ではない」まで書き切っており、抜け道を残していない。
- **AD-10** — 用語集を識別子に射影する規律は、この規模の文書では珍しく実効性がある。追加時の手続き (「PRD §3 用語集への追加と本表への追加を同時に行う」) まで規定しているのが良い。
- **UUID v7 への「ステップ順序とは独立」という注記** — 「id 順に並べればよい」という典型的な誤りを先回りして潰している。
- **パラダイム選択の出自の明示** — 「本スパインの発明ではなく、PRD §8 可搬性が既に規定したものを批准したもの」。下流が原則を再議論する余地を正しく閉じている。
- **Electron 除外の論証** — memlog の「判断は実測報告に基づく制約充足であり嗜好ではない」は、後から蒸し返されない形の記録として模範的。
- **先送りの各項目が理由と再検討条件を持っている** — 特に署名の項 (「v2 の観測は Accessibility 権限を要求し、署名なしでは再ビルドごとに権限がリセットされる可能性が高い」) は、いつ再検討すべきかが読める。
